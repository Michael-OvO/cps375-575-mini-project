# LoRA fine-tuning of 7-9B base models on a multi-task mixture under a token budget: hyperparameters, mixing, selection, failure-driven data

Reading notes: "UNCONFIRMED" marks anything I could only get from a search snippet, a secondary summary, or an abstract (not the paper body/table). Numbers without that tag were read from the primary page itself (via an automated page reader, so table values deserve a spot check before being quoted in a final report). Source inconsistencies are flagged inline.

## 1. LoRA hyperparameters (rank, alpha, modules, LR, batch size, epochs, schedule)

### Takeaway
For instruction-tuning-scale data (10k-100k examples) the best-supported defaults are: LoRA on all linear layers (MLP matters most, attention-only is clearly worse), rank 32-64 as a floor (rank 256 only pays on harder/larger code-style data), LR about 10x the full-fine-tuning LR (roughly 1e-4 to 5e-4 for an 8B model; LR matters more than rank and is the one sweep worth paying for), small-to-moderate batch size, and 1-4 passes with held-out NLL monitoring. Alpha conventions differ between sources (fixed alpha=32 vs alpha=2r vs rsLoRA), and the optimal LR is only "rank-independent" under the convention used, so LR numbers must not be copied across conventions.

### Cited Findings

**Thinking Machines "LoRA Without Regret" (Schulman et al., Sep 2025) - Llama 3 / Qwen3 on Tulu3 and OpenThoughts3**
- LoRA matches full fine-tuning (same sample efficiency and final performance) when the adapter's trainable parameters exceed the information content of the dataset; typical post-training datasets are in this regime. It falls behind once the dataset exceeds adapter capacity. — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)
- Ranks 1 to 512 tested; high rank tracks the full-FT learning curve, low rank departs from it when capacity runs out. — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)
- Optimal LoRA LR is about 10x the optimal full-FT LR in both supervised and RL settings; fitted multiplier across 14 Llama and Qwen models was 9.8. Anecdotal: about 15x for very short runs (under ~100 steps), converging to 10x. — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)
- Optimal LR changes by less than 2x between rank 4 and rank 512 (rank 1 is somewhat lower), under their parameterisation: alpha = 32 with alpha/r scaling, standard PEFT init (A uniform with scale 1/sqrt(d_in), B = 0), same LR for A and B. — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)
- Layer placement: attention-only LoRA underperforms even at matched parameter count; attention-only rank 256 (0.25B params) lost to MLP-only rank 128 (0.24B params); adding attention on top of MLP gave no further benefit. — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)
- Batch size: LoRA is less tolerant of large batches than full FT; the loss gap grows with batch size and is not closed by raising rank (10,000-example OpenThoughts3 subset). Both methods reach best loss at smaller batch sizes. — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)
- Experiments used a constant LR with no warmup or cooldown. — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)
- Capacity rules of thumb: networks store about 2 bits per parameter; LLM datasets cost about 1 bit (0.69 nats) per token; rank-1 LoRA on Llama-3.1-8B has about 3M parameters. — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)
- LoRA costs slightly more than 2/3 of full-FT FLOPs per forward-backward pass. — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)

**Tinker documentation and tinker-cookbook**
- LoRA primer: default rank is 32; LoRA LR is "typically about 10x larger" than full FT; optimal LR does not depend on rank (identical early learning curves across ranks at the same LR); apply LoRA to all weight matrices, especially MLP/MoE; LoRA is less tolerant of large batch sizes and raising rank does not fix it; use a larger rank for large SL datasets. — [Tinker LoRA primer](https://tinker-docs.thinkingmachines.ai/tinker/lora-primer/)
- Rule of thumb for supervised learning: LoRA gives good results when the LoRA parameter count is at least the number of completion tokens with weight = 1; check with `get_lora_param_count(model_name, lora_rank=...)`. — [Tinker LoRA primer](https://tinker-docs.thinkingmachines.ai/tinker/lora-primer/)
- `hyperparam_utils.get_lr(model_name, is_lora=True)`: base LR 5e-5, multiplied by 10 for LoRA, then scaled by `(2000 / hidden_size) ** exponent`, with exponent 0.781 for names containing "llama" and 0.0775 for names containing "qwen"; hidden size 4096 is hardcoded for Llama-3.1-8B and Qwen3-8B. `get_lora_lr_over_full_finetune_lr` ignores its arguments and returns 10.0. Several other model families raise NotImplementedError (uncalibrated). `get_lora_param_count` defaults to rank 32 with MLP, attention and unembedding all enabled. (Obtained from a machine summary of the source file, not a verbatim copy; verify against the file before relying on the constants.) — [tinker-cookbook hyperparam_utils.py](https://raw.githubusercontent.com/thinking-machines-lab/tinker-cookbook/main/tinker_cookbook/hyperparam_utils.py)
- SL hyperparameter tutorial: schedules offered are linear decay to 0, cosine to 0, and constant; example sweep grid LR in {1e-4, 3e-4, 1e-3} x rank in {32, 128}; reference runs on tulu3 used batch size 128 and 780 steps; best reference LRs were 4e-4 to 1e-3; stated guidance: "rank 32 is sufficient for most tasks", LR matters more than rank, rising NLL after an initial drop means LR too high, use held-out `test/nll`. — [Tinker SL hyperparams tutorial](https://tinker-docs.thinkingmachines.ai/tutorials/advanced/sl-hyperparams/)
- UNCONFIRMED (search snippet of the older docs page, which now 404s): the docs call batch size the second most important hyperparameter and say the batch-size recommendations are preliminary and low-confidence. A third-party summary (not official) suggests batch size ~128, scaling LR with sqrt(batch size), and at least 100 steps. — [Tinker SL hyperparams (old URL, 404 at fetch time)](https://tinker-docs.thinkingmachines.ai/supervised-learning/sl-hyperparams)

**Biderman et al. 2024, "LoRA Learns Less and Forgets Less" - Llama-2-7B, code and math**
- Setup: ranks 16, 64, 256; alpha = 2r; all attention + MLP modules; LoRA dropout 0.05; LionW optimizer (not AdamW). IFT data: Magicoder-Evol-Instruct-110K (72.97M tokens) and MetaMathQA (395K pairs, ~103M tokens). — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- HumanEval pass@1 after Magicoder IFT, epoch 4: r=16 0.358, r=64 0.417, r=256 0.498, full FT 0.470. Epoch 8: 0.338 / 0.392 / 0.437 vs full FT 0.497 (LoRA peaks earlier and then declines). — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- GSM8K after MetaMathQA IFT, epoch 4: r=16 0.580, r=64 0.624, r=256 0.625, full FT 0.642 (rank matters much less for math than code). — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- Tulu-v2-mix (~326K samples): LoRA even at r=16 matched full FT on MT-bench within standard error. — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- Learning rates used: code IFT LoRA 2e-4 (r=16, 64) and 1e-4 (r=256) vs full FT 5e-5; math IFT LoRA 1e-4 (r=16, 64) and 5e-5 (r=256) vs full FT 1e-5. LoRA's best LR is roughly an order of magnitude above full FT, and LoRA is more LR-sensitive. Recommendation: sweep 1e-5 to 5e-4 and take the highest stable value. — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- Alpha: alpha = 2r was "crucial" at high rank; for r=256 on Magicoder, alpha=512 beat alpha=256 and alpha=32 across learning rates. — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- Target modules (Magicoder, 4 epochs): attention-only underperformed MLP-only and All; most of the gain of "All" came from MLP. — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- Forgetting (mean of HellaSwag, ARC-Challenge, WinoGrande): code IFT at epoch 16 full FT 0.414 vs LoRA r=64 0.510, r=256 0.517; Tulu at epoch 6 full FT 0.621 vs LoRA r=16 0.657. Weight decay and attention dropout did not reproduce LoRA's learn/forget tradeoff. — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- Diversity: full FT produced the fewest unique strings over 50 HumanEval generations ("distribution collapse"); LoRA sat between base and full FT. — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- Stated best practice: LoRA for instruction tuning rather than continued pretraining; all modules; rank 256 if memory allows (16-64 insufficient for code); alpha = 2r. — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)

**Sebastian Raschka's LoRA experiments (Llama-2-7B, Alpaca 50k / LIMA 1k, QLoRA)**
- Ranks 8, 32, 64, 128, 256, 512 tried; r=256 best. alpha = 2r suggested as the default heuristic; best reported config r=256, alpha=512, though one section reports alpha=128 (0.5x) doing better at r=256 (internal inconsistency in the post). — [Raschka, Practical Tips for Finetuning LLMs Using LoRA](https://magazine.sebastianraschka.com/p/practical-tips-for-finetuning-llms)
- Enabling LoRA on all layers instead of query/value only: trainable params 4,194,304 -> 20,277,248 at r=8 (about 5x), memory 14.18 -> 16.62 GB, with a noticeable performance improvement. — [Raschka](https://magazine.sebastianraschka.com/p/practical-tips-for-finetuning-llms)
- Doubling iterations (about 2 epochs) on the 50k Alpaca set reduced performance; the same decline appeared on 1k LIMA; attributed to overfitting. — [Raschka](https://magazine.sebastianraschka.com/p/practical-tips-for-finetuning-llms)
- Cosine annealing helped SGD noticeably but had little to no effect with Adam/AdamW; AdamW vs SGD memory differs little at r=8 (14.18 vs 14.15 GB) but more at r=256 (17.86 vs 14.46 GB). — [Raschka](https://magazine.sebastianraschka.com/p/practical-tips-for-finetuning-llms)
- QLoRA 4-bit: 14.18 GB and 2.79 h vs LoRA bf16 21.33 GB and 1.85 h, with barely affected modelling quality. Raising max length from 1,304 to 2,048 tokens raised memory from 17.86 to 26.96 GB. — [Raschka](https://magazine.sebastianraschka.com/p/practical-tips-for-finetuning-llms)
- LIMA (1k) with r=256/alpha=512 matched or beat Alpaca (50k); arithmetic benchmarks got worse than the base model after Alpaca tuning (no numbers in text). Run-to-run results at r=8 were described as consistent, with no variance figure given. — [Raschka](https://magazine.sebastianraschka.com/p/practical-tips-for-finetuning-llms)

**rsLoRA (Kalajdzievski 2023)**
- Standard LoRA divides the adapter by the rank, which "results in slowed learning and stunted performance" at higher rank; the paper proves the adapter should be divided by sqrt(rank) instead, letting larger ranks buy better performance at no inference cost. (Abstract only; experiment tables not read.) — [arXiv 2312.03732](https://arxiv.org/abs/2312.03732)

**Other reference recipes**
- Tulu 2 QLoRA recipe: rank 64, alpha 16, dropout 0.1, all attention + feed-forward linear layers, LR 1e-4, 5 epochs, warmup ratio 0.03, effective batch 128, max length 4,096. With it, QLoRA trailed full FT at 7B: average 47.7 vs 53.0, GSM8K 20.5 vs 34.0, AlpacaEval 56.1 vs 73.9; the gap shrank with model size (70B: 71.0 vs 73.4). — [Tulu 2, arXiv 2311.10702](https://arxiv.org/html/2311.10702)
- Tulu 3 full-FT SFT recipe for 8B: LR 5e-6, linear schedule, warmup ratio 0.03, effective batch 128, max length 4,096, 2 epochs (more epochs did not help); sum loss with LR 5e-6 was best. Five seeds at 8B averaged 59.8-60.1 (seed noise about 0.3 points on the average). — [Tulu 3, arXiv 2411.15124](https://arxiv.org/html/2411.15124v2)

### Inferences
- Evaluating the cookbook formula by hand (my arithmetic, from the summarised constants): Llama-3.1-8B LoRA LR = 5e-4 x (2000/4096)^0.781 ≈ 2.9e-4; Qwen3-8B LoRA LR = 5e-4 x (2000/4096)^0.0775 ≈ 4.7e-4. Both sit inside Biderman's recommended sweep range (1e-5 to 5e-4) and near the Tinker reference optima (4e-4 to 1e-3 for other models).
- The alpha conventions are not interchangeable. Tinker/TML fix alpha = 32 with alpha/r scaling (so the multiplier is 1 at r=32 and shrinks at higher rank, compensated by init); Biderman and Raschka use alpha = 2r (multiplier 2 at every rank); Tulu 2 QLoRA used alpha/r = 0.25. The weak Tulu 2 QLoRA result (7B GSM8K 20.5 vs 34.0) used that low multiplier with LR 1e-4, which is consistent with Biderman's observation that PEFT-style small alpha at high rank under-trains; it is likely an under-tuned baseline rather than evidence that LoRA cannot match full FT on a mixture (Biderman found r=16 matched full FT on the same Tulu-v2 mix).
- Capacity check for a budgeted run: rank-1 on an 8B Llama is ~3M params, so rank 32 is ~100M adapter params. By the Tinker rule (params >= completion tokens), rank 32 is adequate up to roughly 100M weighted completion tokens; a 10k-100k example mix (typically 5M-50M completion tokens) is well inside the regime where LoRA should equal full FT, and higher rank mostly buys insurance, not accuracy.
- Evidence conflict on rank: TML/Tinker say rank 32 suffices for typical datasets and LR is nearly rank-independent; Biderman and Raschka see monotone gains up to r=256 on code/Alpaca. The difference plausibly comes from alpha convention, optimizer (LionW vs Adam), multi-epoch training (4-16 epochs in Biderman), and harder code data. Cheapest resolving ablation: rank 32 vs 128 at the same LR, as in the Tinker example grid.
- Epochs: Raschka (2 epochs hurt on Alpaca), Tulu 3 (2 epochs best, more did not help) and Biderman (LoRA HumanEval peaks at epoch 4 then drops) together suggest 1-3 passes for mixed instruction data, with early stopping on held-out NLL; under a token budget, unique data is a better use than extra epochs.
- Warmup/schedule is a low-priority ablation: TML got its results with constant LR and no warmup, Tulu uses linear decay with 3% warmup, and Raschka saw no cosine benefit with AdamW.

### Gaps
- I could not open the current Tinker SL-hyperparameters prose page with the batch-size guidance (old URL returns 404); the batch-size statements above come from a search snippet and the LoRA primer only.
- The `get_lr` constants were read through a summariser that declined to reproduce the code verbatim; they should be checked against the file.
- rsLoRA experimental numbers (ranks, models, perplexity curves) were not retrieved; only the abstract was read.
- No source gave a controlled LR x batch-size interaction table for LoRA on an 8B model, or a direct warmup ablation.
- No direct evidence found for DoRA/other variants in this setting (not searched).

## 2. Multi-task mixing: interference vs transfer, mixture proportions, need for general chat data

### Takeaway
In the Tulu ablations, skills are mostly additive in one model: removing a skill's data hurts that skill sharply and barely moves the others, and removing general chat data costs chat quality (AlpacaEval 12.4 -> 7.5) but not math. There is mild cross-task tension (Tulu 2's mix lost GSM8K/TydiQA points versus V1 while gaining elsewhere; TruthfulQA fell as the Tulu 3 mix grew), and it is larger at 7B than at 70B, so a small general-chat slice plus per-skill data is the supported default.

### Cited Findings
- Tulu 3 8B SFT leave-one-out ablation (Avg / MATH / GSM8K / IFEval / Safety): full mix 60.1 / 31.5 / 76.2 / 72.8 / 93.1; without WildChat 58.9 / 31.8 / 75.8 / 70.1 / 95.2; without safety data 58.0 / 32.6 / 76.9 / 71.0 / 74.7; without persona data 58.6 / 30.1 / 76.8 / 53.6 / 93.9; without math data 58.2 / 23.5 / 64.1 / 70.6 / 93.5. — [Tulu 3, arXiv 2411.15124](https://arxiv.org/html/2411.15124v2)
- WildChat (general chat) mainly helps AlpacaEval 2: 12.4 with vs 7.5 without. Safety data is largely orthogonal to other skills. Persona instruction-following data moves IFEval from 53.6 to 72.8. — [Tulu 3, arXiv 2411.15124](https://arxiv.org/html/2411.15124v2)
- Tulu 3 SFT mix composition (939,344 prompts): Persona MATH 149,960; Evol CodeAlpaca 107,276; WildChat GPT-4 100,000; Aya 100,000; FLAN v2 89,982; NuminaMath-TIR 64,312; OpenMathInstruct 2 50,000; Persona GSM 49,980; WildJailbreak 50,000; WildGuardMix 50,000; Persona Python 34,999; Persona IF 29,980; Persona Algebra 20,000; CoCoNot 10,983; SciRIFF 10,000; No Robots 9,500; OpenAssistant 7,132; TableGPT 5,000. — [Tulu 3, arXiv 2411.15124](https://arxiv.org/html/2411.15124v2)
- Data-size scaling: stratified subsamples at 5%, 10%, 25%, 50%, 75%, 100% of the mix; average performance improved with more data and the full mix was best; GSM8K kept improving up to 100%, while TruthfulQA dropped as the mix grew (figure only, no exact values in text). — [Tulu 3, arXiv 2411.15124](https://arxiv.org/html/2411.15124v2)
- Tulu 2 (Llama-2-7B): ShareGPT-only vs V2 mix: GSM8K 20.0 vs 34.0, Codex-Eval 29.2 vs 36.9, BBH 41.5 vs 48.5, AlpacaEval 72.3 vs 73.9, average 47.0 vs 54.2. V1 mix vs V2 mix at 7B: GSM8K 37.0 vs 34.0 and TydiQA 52.9 vs 46.4 (V2 worse), but Codex-Eval 33.9 vs 36.9 and AlpacaEval 64.5 vs 73.9 (V2 better). Authors conclude no single dataset is best for all tasks. — [Tulu 2, arXiv 2311.10702](https://arxiv.org/html/2311.10702)
- The benefit of the improved mix shrinks with scale: about 13% average improvement at 7B vs about 1% at 70B. — [Tulu 2, arXiv 2311.10702](https://arxiv.org/html/2311.10702)
- Tulu-V2-mix composition (326,154 samples): ShareGPT 114,046; FLAN v2 50,000; CoT 50,000; Evol-Instruct V2 30,000; Open-Orca 30,000; GPT4-Alpaca 20,000; Code-Alpaca 20,022; OpenAssistant 7,708; science 7,544; LIMA 1,030; hardcoded identity 140. — [Tulu 2, arXiv 2311.10702](https://arxiv.org/html/2311.10702)
- Negative transfer from generic instruction data to math: full Alpaca 52k tuning lowered Llama-2-7B GSM8K from 11.50 (base) to 7.00 and MMLU from 45.65 to 44.04, while a 1k longest-response subset raised GSM8K to 14.50. — [Zhao et al. 2024, arXiv 2402.06094](https://arxiv.org/html/2402.06094v1)
- Raschka likewise observed Alpaca-tuned LoRA models scoring worse than the base model on arithmetic benchmarks. — [Raschka](https://magazine.sebastianraschka.com/p/practical-tips-for-finetuning-llms)
- "Less is more" data points: LIMA 1k matched or beat Alpaca 50k in Raschka's QLoRA runs; Platypus used about 25k curated questions and a 13B model trained in about 5 hours on one A100 (abstract). — [Raschka](https://magazine.sebastianraschka.com/p/practical-tips-for-finetuning-llms); [Platypus, arXiv 2308.07317](https://arxiv.org/abs/2308.07317)
- LoRA forgets less than full FT on out-of-domain probes even when trained on a single domain (code IFT epoch 16: 0.517 at r=256 vs 0.414 full FT). — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- Domain-specialised base checkpoints transfer through the same mix: on the Tulu 3 mix, Qwen 2.5 7B reached GSM8K 79.2 / MATH 49.4 vs Llama 3.1 8B 76.2 / 31.5. — [Tulu 3, arXiv 2411.15124](https://arxiv.org/html/2411.15124v2)

### Inferences
- In Tulu 3 the general-chat slice is about 11% of prompts (100k WildChat of 939k) and math about 36% (the five math sets sum to ~334k), code about 15%, explicit instruction-following about 3%. A 3% IF slice bought ~19 IFEval points, so constraint-following data is very token-efficient; math needs volume (and GSM8K kept rising to 100% of the mix).
- The leave-one-out pattern (off-skill deltas mostly within about 1 point, comparable to the ~0.3-point seed noise on the average but larger on single benchmarks) says interference between instruction following, math and code is small at 8B when each has adequate data; the larger risk is a missing skill slice, not a conflicting one.
- A small chat slice is justified for chat-quality metrics, not for math/code: dropping WildChat left MATH/GSM8K unchanged (31.8 / 75.8). If the target evaluation has no open-ended chat-quality metric, the chat slice can be cut to a few percent under a tight budget.
- Generic low-quality instruction data (Alpaca-style, short answers) can actively hurt math, so "general" data should be high quality and long-form rather than bulk.
- All Tulu mixture evidence is full fine-tuning; with LoRA's lower forgetting (Biderman) the regression risk from omitting a slice is plausibly smaller, but that was not directly tested on a mixture ablation.

### Gaps
- No paper found that ablates mixture proportions (e.g. 20/40/40 vs 40/30/30 of IF/math/code) at fixed total tokens for an 8B LoRA; Tulu ablations are leave-one-out at full-FT scale with ~939k prompts.
- LIMA's own ablations (diversity vs quantity, doubling data without gain) were not retrieved from the primary paper; the commonly cited result is UNCONFIRMED here.
- Platypus LoRA settings and its 80% cosine-similarity dedup threshold were not confirmed (only the abstract was read).
- Tulu 3 Figure 4 values at each subsample fraction are not given numerically in the text.
- No evidence gathered on task-balanced sampling vs proportional sampling, or on curriculum/ordering of tasks.

## 3. Data selection under a token budget

### Takeaway
Small selected subsets (roughly 1-15% of Alpaca-class data) repeatedly match or beat full-dataset training, but the simplest heuristics are strong: picking the longest responses beat quality-score filtering and the full set, and random selection is a hard baseline for diversity methods. For synthetic augmentation, targeting data at the student's errors beat generic augmentation at equal volume, and re-augmenting synthetic data hurt.

### Cited Findings
- Longest-response selection (Llama-2-7B, GPT-4 judged "winning score" where 1.0 is parity) vs full Alpaca 52k: longest 1K 1.4505, longest 9K 1.4718, quality-filtered 1K 1.1913, quality-filtered 9K (AlpaGasus-style) 1.3058. Longest vs quality head-to-head: 1.4146 at 1K, 1.2883 at 9K. — [Zhao et al. 2024, arXiv 2402.06094](https://arxiv.org/html/2402.06094v1)
- Same paper, Open LLM Leaderboard style results on Alpaca: base / full / quality / longest-1K: GSM8K 11.50 / 7.00 / 13.00 / 14.50; MMLU 45.65 / 44.04 / 44.80 / 45.70; ARC 50.17 / 50.00 / 54.18 / 54.86; BBH full 36.76, quality 35.74, longest 41.30. Training: AdamW LR 2e-5 (full FT), 3 epochs, batch 128, linear decay with 3% warmup, max length 512 for Alpaca. — [Zhao et al. 2024, arXiv 2402.06094](https://arxiv.org/html/2402.06094v1)
- Same paper's introduction: win/lose rates vs full Alpaca of 68%/20% for longest 1K, 63%/20% for quality 1K, 70%/15% for high-diversity 1K. — [Zhao et al. 2024, arXiv 2402.06094](https://arxiv.org/html/2402.06094v1)
- AlpaGasus: ChatGPT grades each Alpaca triplet 0-5; keeping scores above 4.5 leaves about 9k of 52k (17.75%), and the filtered model outperforms full Alpaca under GPT-4 and human evaluation; the 9k filtered set also beat a random 9k subset. UNCONFIRMED (search summary of the project page/paper, tables not read). — [AlpaGasus project page](https://lichang-chen.github.io/AlpaGasus); [arXiv 2307.08701](https://ar5iv.labs.arxiv.org/html/2307.08701)
- Clustering-and-ranking (CaR): 1.96% of Alpaca (~1,017 instructions) reported to beat full Alpaca by 32.1% on average. UNCONFIRMED and the effect size is unusually large. — [CaR, arXiv 2402.18191](https://arxiv.org/pdf/2402.18191v2)
- MADS diversity-aware coreset: 15% of Alpaca-GPT4 selected by a 3B model reported +2.5% average over full-data training on four larger base models. UNCONFIRMED (search summary). — [MADS, arXiv 2605.30857](https://arxiv.org/pdf/2605.30857)
- Quality filter then k-center greedy coverage: 4,000 selected examples reported to beat tuning on the full 214k dataset. UNCONFIRMED (search snippet; paper not identified with certainty). — [arXiv 2311.15653](https://arxiv.org/pdf/2311.15653)
- Random selection as a baseline: in one extraction of Zhao et al.'s table, diversity-selected 1K scored 0.8913 against random 1K (random won), while quality selection scored above 1. UNCONFIRMED (interpretation by a search summariser, conflicts in tone with the 70%/15% diversity figure vs the full dataset above, which is a different comparison). — [Zhao et al. 2024, arXiv 2402.06094](https://arxiv.org/pdf/2402.06094v1.pdf)
- Targeted vs generic augmentation at ~100 seed examples (Llama-2-7B): GSM8K fine-tune only 1.59, EDA 15.16, AugGPT 18.12, "more real data" 19.86, LLM2LLM (error-targeted) 23.73; CaseHOLD 28.78 / 62.19 / 63.42 / 37.11 / 64.50. On TREC, more real data (89.20) beat LLM2LLM (78.80). — [LLM2LLM, arXiv 2403.15042](https://arxiv.org/html/2403.15042)
- Dedup/near-duplicate filtering thresholds in practice: LLM2LLM filtered generated examples at ROUGE 0.95 (looser than the 0.85 used by Alpaca/Self-Instruct). — [LLM2LLM, arXiv 2403.15042](https://arxiv.org/html/2403.15042)
- More distinct solutions per prompt help in math: rejection-sampling fine-tuning gains more when the augmented samples contain more distinct reasoning paths; SFT accuracy follows a log-linear relation with data amount; LLaMA-7B GSM8K 35.9% with SFT vs 49.3% with RFT data pooled from multiple models (abstract). — [Yuan et al. 2023, arXiv 2308.01825](https://arxiv.org/abs/2308.01825)
- Data volume still matters inside a curated mix: Tulu 3 average and GSM8K rose monotonically from 5% to 100% of the stratified mix. — [Tulu 3, arXiv 2411.15124](https://arxiv.org/html/2411.15124v2)

### Inferences
- Under a token budget, "longest responses" selects exactly the most token-expensive examples; the Zhao et al. comparison is at equal example count (1K vs 1K), not equal tokens. Whether long examples still win per token is untested in the sources read; this is a cheap and decision-relevant ablation (equal-token random vs longest vs quality-filtered).
- The log-linear data scaling (Yuan et al.) plus Tulu 3's monotone curve imply diminishing but non-zero returns: each doubling of unique data buys a roughly constant increment, so selection methods mostly matter when they change which doubling you can afford.
- For math specifically, multiple distinct verified solutions to the same problem behave like new data (RFT), whereas duplicate reasoning paths do not; so dedup on the reasoning/equation level, not on the prompt level. For open-ended instruction data there is no comparable evidence, so prefer more unique prompts there.
- Published selection gains are mostly measured against weak data (Alpaca) with GPT-judged metrics; expect smaller gains when the pool is already curated (Tulu-style), where the evidence says more data wins.

### Gaps
- No source read directly tests "more unique prompts vs more responses per prompt" at a fixed token budget outside math (RFT), and the RFT per-k numbers were not retrieved (abstract only).
- No confirmed numbers for hard-example mining or difficulty-aware selection (loss/perplexity-based, gradient-based such as LESS) on 7-9B models; a LESS blog post surfaced in search but was not read.
- AlpaGasus, CaR, MADS and the k-center result are unverified against their tables.
- No quantitative evidence gathered on near-duplicate removal by embedding similarity (e.g. Platypus's threshold) and its effect size.

## 4. On-policy and failure-driven methods (RFT / expert iteration / STaR / ReST / LLM2LLM), rounds, collapse risks

### Takeaway
Verifier-filtered self-generated data and teacher data targeted at student errors both give large gains in low-data regimes, with most of the benefit in the first few rounds; the three procedural choices with measured effects are (a) iterate rather than generate once, (b) generate only from original seed/real examples, never from synthetic ones, and (c) retrain from the base checkpoint each round on accumulated data rather than continuing to fine-tune. Collapse risk is documented as reduced output diversity and in-domain gains with weaker generalisation, and is mitigated by accumulating real plus synthetic data rather than replacing.

### Cited Findings
- LLM2LLM main results (Llama-2-7B student, GPT-3.5 teacher, 10 rounds), baseline -> LLM2LLM test accuracy on GSM8K by seed size: 74 examples 0.99 -> 19.56 (391 augmented); 373 examples 9.63 -> 27.07; 747 examples 21.27 -> 30.93; 3,737 examples 33.89 -> 38.67; full 7,473 examples 36.01 -> 41.24 (14,925 augmented). Gains shrink as seed data grows. — [LLM2LLM, arXiv 2403.15042](https://arxiv.org/html/2403.15042)
- Iterative vs one-shot at equal augmented volume (100 seeds): GSM8K 23.73 (10 steps, 471 augmented) vs 16.30 (1 step, 490 augmented); CaseHOLD 64.50 vs 59.94. — [LLM2LLM, arXiv 2403.15042](https://arxiv.org/html/2403.15042)
- Augmenting only from seed errors vs also re-augmenting synthetic examples: GSM8K 23.75 (471 augmented) vs 18.32 (4,302 augmented); CaseHOLD 64.50 vs 63.75. — [LLM2LLM, arXiv 2403.15042](https://arxiv.org/html/2403.15042)
- Retraining from scratch each round vs continuing fine-tuning: GSM8K 23.75 vs 14.71; CaseHOLD 64.50 vs 60.50. — [LLM2LLM, arXiv 2403.15042](https://arxiv.org/html/2403.15042)
- Teacher quality (GSM8K, 74 seeds): Llama-2-70B 11.83, Airoboros 15.01, GPT-3.5 19.56, GPT-4-Turbo 19.79; at 149 seeds 17.59 / 19.33 / 25.70 / 25.78. — [LLM2LLM, arXiv 2403.15042](https://arxiv.org/html/2403.15042)
- Per-round shape: accuracy rises rapidly in the first few iterations, especially at low data (figure description, no per-round numbers in text). LLM2LLM settings: full FT, LR 2e-5, batch 128, cosine schedule, warmup 0.03, max length 1,024. — [LLM2LLM, arXiv 2403.15042](https://arxiv.org/html/2403.15042)
- Rejection-sampling fine-tuning: LLaMA-7B on GSM8K 35.9% (SFT) -> 49.3% when rejection-sampled correct solutions from multiple models are pooled; benefit scales with the number of distinct reasoning paths (abstract). — [Yuan et al. 2023, arXiv 2308.01825](https://arxiv.org/abs/2308.01825)
- STaR (Zelikman et al. 2022): loop of generate rationales, keep those reaching the correct answer, fine-tune, repeat; adds "rationalization" (give the answer as a hint for failed problems). CommonsenseQA with GPT-J: 72.3-72.5% with rationalization vs 68.8% without and about 60% for direct answer fine-tuning; comparable to a 30x larger fine-tuned model (73.0%). Requires above-chance few-shot performance to bootstrap; binary tasks admit many bad rationales. UNCONFIRMED at table level (search summaries of the paper). — [STaR, arXiv 2203.14465](https://arxiv.org/pdf/2203.14465)
- ReST meets ReAct: growing-batch RL with AI feedback; after two iterations a fine-tuned small model reaches comparable performance to the large agent with about two orders of magnitude fewer parameters (abstract; no per-round numbers). — [arXiv 2312.10003](https://arxiv.org/abs/2312.10003)
- Collapse: accumulating real and synthetic data across generations avoids model collapse, while replacing old data with new synthetic data degrades successive models. UNCONFIRMED (search summaries). — [Gerstgrasser et al., arXiv 2404.01413](https://fugumt.com/fugumt/paper_check/2404.01413v2_enmode); [Collapse or Thrive, arXiv 2410.16713](https://arxiv.org/html/2410.16713v1)
- Self-improvement on reasoning can produce "superficial" gains: in-domain accuracy rises while out-of-domain generalisation drops and outputs become more deterministic. UNCONFIRMED (search summary of an EMNLP 2025 paper). — [EMNLP 2025 main.301](https://aclanthology.org/anthology-files/pdf/emnlp/2025.emnlp-main.301.pdf)
- Related diversity evidence: full FT reduces unique generations more than LoRA (50 HumanEval samples). — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)
- RL-style on-policy training fits LoRA well: LoRA matched full FT in RL even at rank 1, with a wider range of good LRs; a MATH RL run supplies about 320,000 bits (about 10,000 problems x 32 samples) vs about 3M parameters at rank 1. — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)

### Inferences
- Decision rule from LLM2LLM: the on-policy loop pays most when the student's baseline is weak for the amount of real data (gain +18.6 points at 74 seeds, +5.2 at the full 7.5k). With a 10k-100k curated mix, expect single-digit gains from error-targeted rounds and prioritise them for the weakest skill.
- A budget-friendly protocol consistent with the ablations: train, evaluate on a held-out slice of training prompts, have the teacher write new problems similar to the failed real ones (not to failed synthetic ones), add to the pool, and retrain from the base model; 2-3 rounds captures most of the curve (ReST used 2; LLM2LLM gains are front-loaded). Retraining from scratch each round multiplies training tokens, so the round count is the main cost lever.
- Teacher strength mattered much more between open 70B and GPT-3.5 (+8 points) than between GPT-3.5 and GPT-4-Turbo (+0.2), so a mid-tier teacher is sufficient for grade-school-math-level targets.
- For self-generated data with a verifier (RFT/STaR), keep several distinct correct solutions per problem and dedupe by reasoning path; always keep the original real data in the pool (accumulate, do not replace) and track an out-of-domain metric plus an output-diversity metric per round to catch superficial gains.
- Using LoRA rather than full FT is itself a mild guard against diversity collapse (Biderman).

### Gaps
- LMSI (Huang et al. 2022) numbers were not retrieved; no confirmed figures for self-consistency-filtered self-training.
- "Teaching via targeted data generation" style papers other than LLM2LLM were not found/read; no confirmed per-round accuracy tables for any method (only LLM2LLM's figure description and ReST's "two iterations").
- RFT paper body not read: per-k sample counts, 13B results and the dedup-by-equation details are unconfirmed.
- No direct measurement found of how many rounds until diversity loss becomes harmful for an 8B LoRA student.
- Collapse findings come from secondary summaries and from generative-model settings that differ from verifier-filtered fine-tuning.

## 5. Training a base (non-chat) model through a chat template

### Takeaway
The chat-template choice itself is worth about 1 point on the Tulu 3 average for a Llama 3 base model (51.6 to 53.0 across five templates), so it is a minor lever; the failure modes that actually break runs are stop-token ones: EOS labels masked out when pad == EOS, and a mismatch between the turn-end token the template emits and the tokenizer/generation EOS. Controlled evidence on assistant-only loss masking was not found.

### Cited Findings
- Tulu 3 chat-template ablation (Llama 3.0 base, early SFT mix), average score: newline-replaced-with-EOS variant 53.0; Zephyr 52.9; Tulu 3 template (trailing newline removed) 52.8; Tulu 2 template 52.6; Llama 3 native template 51.6. The team avoided the EOS-replacement variant to prevent generation inconsistencies later in the pipeline. — [Tulu 3, arXiv 2411.15124](https://arxiv.org/html/2411.15124v2)
- Tulu 3 found sum-reduced loss (every token weighted equally, independent of padding and gradient accumulation) with LR 5e-6 worked best versus mean loss, at the cost of needing an adjusted LR. — [Tulu 3, arXiv 2411.15124](https://arxiv.org/html/2411.15124v2)
- Sequence-length settings in reference recipes: Tulu 3 max 4,096 tokens; Tulu 2 full FT 8,192 and QLoRA 4,096; LLM2LLM 1,024; Zhao et al. 512 for Alpaca and 2,048 for WizardLM. — [Tulu 3](https://arxiv.org/html/2411.15124v2); [Tulu 2](https://arxiv.org/html/2311.10702); [LLM2LLM](https://arxiv.org/html/2403.15042); [Zhao et al.](https://arxiv.org/html/2402.06094v1)
- Memory cost of length: raising max length from 1,304 to 2,048 tokens raised QLoRA memory from 17.86 to 26.96 GB on a 7B model. — [Raschka](https://magazine.sebastianraschka.com/p/practical-tips-for-finetuning-llms)
- EOS masking failure: when pad and EOS are the same token, common collators set every pad-position label to -100, which masks all EOS labels; the model gets no gradient on stopping and never learns to stop. Recommended fix: keep PAD distinct from EOS during fine-tuning. (Practitioner forum write-up, not a controlled experiment.) — [HF forum write-up](https://huggingface.co/datasets/John6666/forum2/blob/main/qwen_eos_token_1.md)
- Qwen3 Base case: the chat template emits `<|im_end|>` while a tokenizer update set EOS to `<|endoftext|>`, so a base model fine-tuned through the chat template no longer has its turn-end token recognised as EOS at inference unless the stop token is set explicitly. — [The Kaitchup, Qwen3 im_end post](https://kaitchup.substack.com/p/qwen3-when-im_end-suddenly-becomes)
- Stop-token ids differ by family; one guide lists Llama 3.x Instruct stop ids [128001, 128008, 128009] and Qwen 3 chat [151645, 151643]; `generation_config.eos_token_id` is not used in the training loss, so fixing it changes inference stopping only. UNCONFIRMED (secondary cookbook-style source). — [Sabr Research cookbook](https://sabrresearch.com/cookbooks/fix-eos-token-infinite-generation)
- Tinker's capacity rule counts only "completion tokens with weight = 1", i.e. its supervised pipeline weights loss on the completion (assistant) tokens. — [Tinker LoRA primer](https://tinker-docs.thinkingmachines.ai/tinker/lora-primer/)
- Base vs chat checkpoints: Biderman used the Llama-2-7B base model with the chat tokenizer for IFT; TML's experiments include Qwen3-8B-Base and Qwen3-30B-A3B-Base. — [arXiv 2405.09673](https://arxiv.org/html/2405.09673v2); [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)

### Inferences
- For a base checkpoint, the turn-end token (`<|eot_id|>` or `<|im_end|>`) is essentially untrained, so every training example must end with it inside the loss mask, and inference must list it as a stop token; verify by checking that the last supervised label of each example is the turn-end id and that greedy decoding on a held-out prompt terminates. This is the cheapest high-value check before any ablation.
- Runaway generation interacts with greedy decoding: a model that has not learned to stop will loop until max tokens, which both wastes inference budget and can corrupt answer extraction. Tulu 3's reluctance to use the EOS-substitution template (despite its top score) reflects the same concern about stop-token consistency.
- Template choice is a roughly 1-point effect, below most data effects, and comparable to 3x seed noise; pick the model family's native role tokens (so any embedding prior is reused) and do not spend budget ablating it.
- Under a token budget, the max-length cap interacts with data selection: long reasoning traces dominate token spend, and truncation that cuts the final answer or the EOS removes exactly the stop signal; filter or drop over-length examples rather than truncating them.
- Training on assistant tokens only is the convention in Tinker's pipeline and standard chat SFT; the adapter-capacity rule should therefore be applied to completion tokens, not total tokens.

### Gaps
- No controlled ablation found comparing assistant-only loss vs full-sequence loss for instruction tuning of a base model; I found no reliable source on its effect size.
- No published measurement found of how many examples a base model needs to reliably learn an untrained end-of-turn token under LoRA, or whether the unembedding/embedding rows must be trainable (Tinker's param-count helper includes an "unembed" component, but I did not confirm what it adapts).
- Tulu 3's BOS-token finding and base-vs-instruct starting-checkpoint comparison were not in the portions of the paper read.
- No quantitative evidence found on greedy-decoding stability (repetition loops) as a function of training settings; the statements above are inference from stop-token mechanics.
