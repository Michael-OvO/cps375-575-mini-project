## 1. Bad-case analysis: where the points are

This is diagnosis only. No public item is ever used to choose training prompts.

**Public per-item results across SFT versions v1, v2, v3, v4** (inspect logs):

| Benchmark | n | Right in all 4 | Never right | Flipping | v4 right | v4 wrong but solved by an earlier version | Ceiling if every once-solved item is solved |
|---|---|---|---|---|---|---|---|
| MATH-500 | 500 | 287 | 80 | 133 | 71.8% | 61 (12.2 pts) | 84.0 |
| MBPP | 257 | 151 | 39 | 67 | 73.2% | 30 (11.7 pts) | 84.8 |
| IFEval prompt-strict | 541 | 258 | 89 | 194 | 70.1% | 73 (13.5 pts) | 83.5 |

- **Flipping items** are items the model family gets right only some of the time. That is the
  0 < p < 1 zone where RL sharpening works (Section 4), measured.
- **The never-right core** is out of reach for short RL, which sharpens and does not add capability:
  - math: 52 of the 80 are level 5;
  - MBPP: 39 tasks;
  - IFEval: 89 prompts.
- **Math v4 failures (141):**
  - 60 wrong but flipping;
  - 70 wrong and never right;
  - 11 with no `ANSWER:` line (loops and truncation).
  - The flipping ones sit at levels 3–4 (36 of 60); the never-right ones at level 5 (52 of 80).
- **MBPP v4 failures (69):** all are wrong code (30 flipping, 39 never right). None are format
  failures.
- **IFEval v4 failures (174 failed instructions of 834)** are mostly counting constraints:

  | Type | Failed / total |
  |---|---|
  | `keywords:frequency` | 24 / 42 |
  | `length_constraints:number_words` | 23 / 52 |
  | `keywords:forbidden_words` | 17 / 49 |
  | `length_constraints:number_sentences` | 17 / 52 |
  | `keywords:letter_frequency` | 16 / 33 |
  | `change_case:capital_word_frequency` | 12 / 25 |
  | `change_case:english_lowercase` | 10 / 39 |

  All are deterministic checker types that RL trains well. About half of each type's failures were
  solved by v1 or v3.
- **Our IF verifier agrees with the official prompt-strict result on 541 of 541 v4 IFEval items**,
  so the IF reward is the graded metric.
- **Dev transitions** (dev split: math 325, code 337, IF 331 with seen and unseen ids in v1):

  | | Never right | Flipping | Always right |
  |---|---|---|---|
  | Math | 63 | 73 (22%) | 189 |
  | Code | 45 | 91 (27%) | 201 |
  | IF | 128 | 108 (33%) | 95 |

  82 of the 128 always-wrong IF items are unseen types, which is the generalization gap.

**What this means for the design:**
1. Every task has 12–13 points of measured headroom in the reachable zone.
2. IF counting types get extra weight in the IF pool (Section 6).
3. Truncation and loops are a small share of math failures (11 of 141); truncation still gets reward 0.

**Quantitative IFEval expectation.**
- Let f = the share of the 73 reachable failing prompts that RL fixes, g = the share of the 121
  currently-right flipping prompts it breaks, and h = the share of the never-right core it fixes.
- With f = 0.4, g = 0.05, h = 0.05: prompt-strict +4.3 to +5. Instruction-level metrics move about the
  same in proportion. final_acc ≈ 75.9 + 4–5 ≈ **80**.
- f = 0.25 gives about 78.5; f = 0.55 gives about 82.
- **So 80 is the median outcome, not the floor: P(IFEval ≥ 80) ≈ 45–50%.**
- MATH-500: 72–75. MBPP: 73–76.

## 2. Goal and success criteria

**Accept rl1** only if no area drops beyond 2 standard errors against v4 and at least one area gains.
An area is judged on its public score, its dev score and the final **vault** confirmation together.
The team decides and uploads.

**Rule 2 (hard):** no IFEval, MATH-500, MATH test, MBPP or HumanEval item as a prompt.
- Also excluded: dev and vault items, dev-only and `HELD_OUT` types, IFBench test prompts, and trap

- The leakage filter gains HumanEval and IFBench test, and `code_tasks` is re-checked against

## 4. Starting checkpoint (Phase 1)

1. Clear the TTL on `weights/v4-step1500` (Section 0).
2. Replay as a **new run name `v4r`** that reads `runs/v4/train.jsonl`. Running under `--name v4`
   would truncate v4's `train_log.jsonl` and delete its `checkpoint.json` [R-H3].
3. Resume the state with its optimizer. Replay 0-indexed steps 1501–1687 at
   `lr_at(step, 1688, 4.7297908091376354e-4)`, with `--no_publish`.
4. Save the final `weights/` and sampler checkpoints.

- **Cost:** about $4.9.
- **Gate** [R-M5]: compare v4r's dev items with v4's stored per-item results in
  `runs/v4/errors/*.jsonl`.
  - McNemar p > 0.05 in every area, and per-item agreement ≥ 85%.
  - A fixed "within 1 point" rule is not used, because numerics flips alone give an SD of about
    1.5 points at n ≈ 330.

## 5. Objective and estimator

**Objective.** J = Σ_d w_d E_{x∼D_d} E_{y∼π_θ(T=1)}[R_d]. Per group: `A_i = r_i − r̄`, so
E[A_i ∇log π] = ((G−1)/G)∇J. The token-sum loss is exact REINFORCE. Dropping constant groups is
unbiased, since they have A = 0. Per-answer length normalization and per-group std normalization stay
rejected.

**Per-domain scaling, rebuilt** [R-M1].
- c_d = 1 / (S_d · L_d), where S_d and L_d are an **EMA over previous steps only**, initialized from
  Phase 2:
  - S_d is the std of centered advantages in non-constant groups;
  - L_d is the mean response tokens.
- Because c_d is fixed before the current samples are drawn, the step estimate is exactly
  c_d·((G−1)/G)∇J_d. That is unbiased per domain, with no same-sample ratio bias.
- Dividing by L_d as well removes the token-sum length weighting across domains. Each domain's
  expected Σ|A|·tokens per sample is then equal, so the group counts w_d set the gradient shares.
- Only the ratios between domains matter, since Adam removes global scale.
- Per-domain Σ|A|·tokens shares are logged every step.

**Teacher term ordering, if on** [R-M1c]:
1. Scale the task advantage by c_d.
2. Add `−λ(log p_θ − log q)` per token, with λ relative to the unit-scaled advantage.
3. Compute S_d without the teacher term and without constant groups.

**Why this suits greedy evaluation.** Short RLVR sharpens toward answer modes that already pass. The
reachable zone is measured in Section 1.

**No KL to v4.** At β = 0.02 the per-token penalty is about 2e-4 against |A| ≈ 0.4. A KL monitor
replaces it.

## 6. Rewards (pure functions; Phase 0 tests on real data)

**Truncation.** `stop_reason == "length"` gives R = 0 for every task. This is stricter than the eval:
- math: the eval would still read a final `ANSWER:` inside a loop;
- code: the eval's fallback extraction could still pass [R-M7].

The difference is deliberate, to teach stopping, and affects about 2% of outputs.

**Math.** R = 1 if `equivalent(answer_of(y), target)`; this is the graded scorer itself.
- No other guards [R-H1]. Because the reward is the graded scorer, a hack would also fool MATH-500, so
  extra guards can only add false negatives. Hedging with several `ANSWER:` lines gains nothing,
  because the scorer reads the last one.
- Targets: MATH train boxed answers, or teacher problems where at least two independent solutions
  agree.

**IF, routed by constraint id** [R-C3]:
- the 25 IFEval ids → the official `instruction_following_eval` (the graded code);
- IFEvalG and IFBench-train ids → `pipeline/constraints/ifevalg`;
- project ids → `pipeline/constraints/extra`.

All three use the official 8 loose variants, and langdetect is seeded (`DetectorFactory.seed = 0`).

- **Reward:** R = ¼(ps + pl) + (s + l)/(4k̄), with k̄ = 1.54.
  - Its maximum grows with k: 1.15 at k = 1, 2.12 at k = 5. This matches IFEval's instruction-level
    weighting, as intended [R-M2].
  - For selection, a prompt's normalized pass rate is p̂ = mean R / max R.
- **Phase 0 test:** every constraint kwargs dict in the pool builds under its routed checker. The
  pass/fail results must match the stored verification of the IF-RLVR SFT data.

**IF quality gate (R = 0), precise and exempted per type** [R-C4]:

| Rule | Exempt types |
|---|---|
| v4 SFT label-line filter | none |
| Placeholder copies `[name]`, `{x}`, `<placeholder>` | `detectable_format:square_brackets`, `bigram_wrapping`, `title`, `detectable_content:number_placeholders`, and any type whose kwargs ask for brackets |
| Same sentence repeated 3 or more times | `copy:*`, `combination:repeat_prompt`, `combination:two_responses` |
| Two or more identical list items | none |
| Self-evaluation lines ("I have followed all…", "(Word count: N)") | none |
| Under 4 words | letter, length and short-answer types (`letters:*`, `length_constraints:*` with upper bounds) |

The generic 3-gram rule and the short-bullet rule are removed.

**Phase 0 gate:** run the quality gate over all verified teacher answers in `data/if_rlvr.*.jsonl` and
`data/if_responses.jsonl`. It must fire on under 1% of answers for **each** constraint type before
Phase 2.

**Code.** R = 1 only if all of these hold:
1. Extraction uses `extract_code`.
2. The answer is harness-safe: `preflight.top_level_unsafe(code, tests)` is false. Only defs, classes
   and imports of modules the tests use are allowed at top level. This protects the body-only
   harnesses that cost v2 HumanEval 67 → 31 [R-C6].
3. **AST guards** do not fire [R-H2]. They forbid calls or imports of:
   - `sys.exit`, `os._exit`, `os.kill`, `os.system`, `exit()`, `quit()`;
   - `subprocess`, `unittest.mock`, `inspect`, `ctypes`, `importlib`;
   - `sys._getframe`, `gc`;
   - assignments to `builtins`, `print` or `AssertionError`;
   - `__eq__`/`__ne__` definitions in any class. The Phase 0 reference-solution gate confirms this
     rule costs nothing on legitimate code.

   Benign `sys.maxsize` and `os.path` uses are allowed.
4. All visible and hidden asserts pass. The program is passed via `-c`, never written to disk, and a
   per-run random sentinel printed after the last assert must appear in stdout.
5. A type check in the harness: no result compared in an assert is a `unittest.mock` object.

**Phase 0 gate:** the guards fire on about 0% of the 20,246 reference solutions, and every reference
solution scores R = 1.

**Sandbox** [R-C1, R-M12]:
- `sandbox-exec` profile denying network, `process-fork` and writes outside the temp dir;
- `RLIMIT_CPU` 10 s plus a 30 s wall timeout (the MBPP scorer's);
- a psutil RSS watchdog killing at 512 MB;
- a bounded pool of 12 workers;
- stdout captured up to 64 KB;
- `python -I` and a fresh temp dir.

**Tests:** a memory bomb, a fork bomb, a network call, a file write, an infinite loop, exit-early,
`unittest.mock.ANY`, frame-reading of the sentinel, always-equal.

## 7. Prompt pools and selection

**Sources:**

| Task | Source | Exclusions |
|---|---|---|
| Math | MATH train; teacher problems with agreed targets | dev and vault |
| IF | `if_rlvr_prompts`; our sampler in train mode | `HELD_OUT`, `DEV_ONLY_IDS`, dev and vault, IFBench test, trap prompts |
| Code | `code_tasks`; `oci_tasks` | `is_code_dev`; < 5 asserts; **any stub passes all asserts** (about 199 OCI, 0 ours) [R-C2]; harness-unsafe reference |

- Trap prompts are 50 fresh IF prompts written by us, where a hack is the easy path. They are kept out
  of every pool by id and n-gram [R-M10].
- Math and code use the harness template only.

**IF mix:**
- Constraint count: 60% with 2–3 constraints, 25% with 1, 15% with 4–5. Prompts with 5 constraints
  come from `if_rlvr_prompts`, because the sampler's `K_WEIGHTS` stops at 4.
- At most 120 prompts per type, with wide parameter ranges.
- The IFEval counting types in Section 1 get 1.5× sampling weight within their bins.

**Calibration (Phase 2)**
1. 300 prompts per task, G = 8 at T = 1 plus one greedy decode, on v4r.
2. **Coarse strata with Beta(1,1) shrinkage** [R-M3]:
   - math: subject × level band (1–3, 4, 5), 21 strata;
   - IF: type family × count bin (1, 2–3, 4–5), about 12 families;
   - code: source × category.
3. Record: p̂, greedy pass rate, informative rate, length, truncation, gate and guard rates, and the
   visible-pass/hidden-fail rate.
4. **Sanity gate:** read 30 rollouts per task by hand; every reward branch must fire on real outputs.
   **Plus** the teacher pre-flight (Section 8b).

**Selection** [R-C5]:
- Pass-rate bands apply **per stratum**, because per-prompt p is unknown for unseen prompts. Within
  strata, prompts are drawn at random, and constant groups are dropped online.
- Stratum weight is proportional to `n_s · E[p̂(1−p̂)]_s · (1 + g_s)`, where g_s is the greedy-fail
  rate.
- Strata with an informative rate under 0.25 are excluded, at the start and at the step-60 re-check
  alike.
- **IF:** strata with p̂ ≤ 0.6 are preferred, but the constraint-count mix wins where they conflict
  [R-M2].
- **Task weights:** prior 40 / 35 / 25. Each moves at most ±10 points toward
  `(informative rate) × (dev fail rate) / (cost per group)`. Dev rates only, never public [R-M10].
- **Step-60 re-check:** reweight from the running logs. The pause rules reset at that point [R-M4].
- One pass, no repeated prompts. The step count × 64 prompts are drawn up front and the order is saved,
  for resume.

### 8b. Optional teacher term (397B, IF only): the pre-flight decides

All checks run on Phase 2 IF rollouts, costing about $2.

1. **Re-rendering** [R-M9]:
   - The prompt goes into the Qwen3.5 template (non-thinking, empty think block); the completion
     tokens stay unchanged.
   - Mask the first completion token (role_colon's leading space) and the trailing "\n\n" and stop
     tokens.
   - Unit tests cover the boundary tokens.
2. **No thinking pull:** the mean log-ratio over completion tokens 2–6 is no more than 2× the mean
   elsewhere.
3. **Signal:** the **per-token mean** log-ratio separates reward-1 from reward-0 samples with
   AUC ≥ 0.65.
4. **Cost:** the measured cost per step with the term is ≤ $0.65.
5. **Rules:** staff confirm the teacher is allowed.

If any check fails, the run is RLVR-only.

## 9. Phases, ledger and pause rules

**One persistent spend ledger** (`runs/rl1/ledger.jsonl`) [R-H7]:
- every Tinker call, in every phase, logs its tokens and cost at list prices;
- it survives restarts;
- it refuses new work that would exceed the approved cap.

| Phase | What | Tier S | Tier L |
|---|---|---|---|
| 0 | Code; tests; data gates (IF gates < 1% per type, guards ≈ 0% on references, kwargs build, leakage incl. HumanEval and IFBench) | $0 | $0 |
| 1 | Clear TTL; replay to v4r; dev equivalence check | $6 | $6 |
| 2 | Calibration and teacher pre-flight | $4.5 | $4.5 |
| 3 | Smoke: 3 steps × 8 groups | $1 | $1 |
| 4a | **Pilot: 40 steps, then human review** | $18–24 | $18–24 |
| 4b | Continue from saved state (if 4a passes review) | to $55 total main | to $105 total main |
| — | Checkpoint dev evals, every 20 steps at about $1.2 each (greedy dev 1,123 items + pass@8 and pass@1 on 100 per task + 50 traps) | about $7 | about $14 |
| 5 | Final: public, proxies, **vault** for the best 1–2 checkpoints | $5 | $5 |
| | **Cap** | **$80** | **$135** |

**Pause rules** [R-M4]. Each is per domain, over 10-step windows, relative to the Phase 2 baseline,
with a minimum absolute change. A pause saves state and waits for review:
- mean length > 2× baseline, or truncation > 2× baseline + 2 points;
- `kl_sample_train_v1` > 0.01, or KL to v4 > 0.05 nats per token. The KL monitor scores 64 rollouts
  under v4 every 20 steps;
- IF gate or code guard rate > baseline + 3 points; visible-pass/hidden-fail > baseline + 3 points;
- trap hack rate > baseline + 10 points;
- any dev area more than 2 standard errors below v4;
- per-domain smoothed reward falling for 30 steps (reset at step 60).

**Hard stops:** the spend cap, or 3 consecutive crashed steps.

**Logged every step, per domain:** reward, informative rate, effective batch, Σ|A|·tokens share,
length, truncation, entropy, ratio statistics, gate and guard rates, ledger total.

## 10. Evaluation and selection [R-H5]

- **Checkpoint dev eval** (greedy, dev split only: math 325, code 337, IF 461) every 20 steps. Also
  pass@1 at T=1 and pass@8 on 100 items per task.
- **Dev sum** = math + code + IF, where IF is final_acc pooled over all 461 items.
- **Selection:** maximize the dev sum, subject to:
  - every area within 1 standard error of v4;
  - the pooled unseen + unseen_new IF score not below v4's minus 1 standard error.
- **Statistics:**
  - At n ≈ 330 with about 10% discordance, the paired 2-standard-error threshold is about 3.5 points
    per area. 80% power needs about 4.5 points.
  - Smaller math and code gains cannot be confirmed on dev alone.
  - Picking the best of k checkpoints inflates the winner by about 1.3σ for k = 6 and 1.6σ for k = 11.
- **Confirmation on independent data:** public scores, the vault (used only here), MATH test minus
  MATH-500, and HumanEval. All are paired against v4, using McNemar or paired bootstrap.

## 11. Risks and closures

| Risk | Closure |
|---|---|
| Reward hacking | Graded scorers as rewards; AST guards and sentinel; mock check; per-type IF gates; trap prompts; pause rules |
| Gates or guards zeroing correct answers | Phase 0 data gates on all verified answers and references |
| IF reward not matching the graded checker | Id routing; official checker for the 25 IFEval ids; agreement measured on 541 of 541 |
| Sandbox failure on macOS | No `RLIMIT_AS`; RSS watchdog, fork deny, worker pool; bomb tests |
| Harness-unsafe code learned | `top_level_unsafe` in the reward |
| Losing v4 records or state | New run name v4r; TTL cleared |
| Dev and vault honesty | Dev-only selection; vault only at the end; public never used for selection |
| Overspend | Persistent cross-phase ledger with a hard cap |
| Crash mid-run | Resume JSON every 10 steps; caffeinate on AC power |
