# RL round (rl1) design

Date: 2026-11-16. Status: draft for team review. Nothing in this spec has been run yet, except the two
infrastructure probes marked **measured**.

## 1. Goal and success criteria

Start from the v4 SFT model (IFEval 75.9, MATH-500 71.8, MBPP 73.2; dev math 71.4, dev code 70.3;
HumanEval 75.6) and run one round of RL whose rewards are checked by code (IF checkers, math answer
equivalence, unit tests).

- **Accept rl1 as the submission** only under the standing acceptance rule: no area drops by more than
  about 2 standard errors against v4, and at least one area gains. "Area" means public score plus its
  dev and held-out proxy together (Section 9).
- **Budget:** at most $80 of Tinker spend for everything in this spec, enforced in code (Section 8).
- **Rule 2 (hard):** no IFEval, MATH-500, MATH test, MBPP or HumanEval item is used as a prompt, in any
  form. Dev items and dev-only IF constraint types are excluded as well, so the dev and proxy numbers stay
  honest measures of generalization.

**Honest expectation.** Published RLVR on top of SFT (Tulu 3: +1–4 points per verifiable task) and the
cookbook's own MATH run point to these gains:

| Area | v4 | Expected after rl1 | Chance of reaching 80 |
|---|---|---|---|
| IFEval | 75.9 | 77–81 | about 35% |
| MATH-500 | 71.8 | 72.5–75 | under 5% |
| MBPP | 73.2 | 73–76 | under 5% |

80 in all three in this round is very unlikely. The realistic aim is about +2 to +4 on the sum without
losing anything on the held-out proxies.

## 2. Facts checked in code (not assumed)

1. **v4 cannot be the RL starting point as saved. Measured:**
   - Tinker rejects `sampler_weights/v4` for training ("only weights/ checkpoints are supported").
   - `train_sft.py` saves resumable state every 250 steps but not at the end, so the latest trainable
     state is `weights/v4-step1500`.
   - That state loads, optimizer included.
   - Its 7-day TTL expires around **2026-11-22**, so Phase 1 must run before then.
2. **Advantages:** the cookbook computes `A_i = r_i − mean(r_group)` (`rl/data_processing.py`). It does
   not divide by the group std and does not normalize per answer length. That is the estimator derived
   in Section 4.
3. **KL penalty:** it is added to the per-token advantages as `β·(mean Δ − Δ_t)`, where
   `Δ_t = log π_sample(y_t) − log π_ref(y_t)` (`rl/metrics.py`). The reference model is a sampling
   client, so v4's `sampler_weights` path works as the reference.
4. **Per-task token caps:** the rollout runner reads `env.rollout_limits`
   (`rl/rollout_runner.py`, line 329). The IF env can cap at 1,024 tokens while math and code use the
   global 4,096.
5. **Mixed tasks in one batch:** each `EnvGroupBuilder` is its own group, and advantages are centered
   per group. Math, IF and code groups can share a batch without their rewards mixing.
6. **Tested reference config:** the cookbook reports MATH RL on Qwen3.5-9B with `importance_sampling`,
   lr 2e-5, G=16, 64 groups per batch, 180 steps. On GSM8K, G=8 with 64 groups per batch was also run
   (lr 8e-5).
7. **Eval prompts:** math uses inspect's `USER_PROMPT_TEMPLATE`. MBPP uses inspect's template with our
   own three few-shot examples. Both are built by `pipeline/formats.py`, stripped the same way the
   inspect adapter strips them. Eval decoding is greedy, capped at IFEval 1,024 and MATH/MBPP 4,096
   tokens.

## 3. Starting checkpoint: replay v4 to a trainable state (Phase 1)

SFT batches are deterministic (`batches()` walks `runs/v4/train.jsonl` in order), and the learning rate
is `lr_at(step, 1688, base_lr)`.

1. Resume `weights/v4-step1500` with its optimizer.
2. Replay steps 1501–1687 with the same batches and learning rates.
3. Save both a `weights/` state and sampler weights as **v4r**.

- **Cost:** 187 steps × 32 examples × 559 tokens ≈ 3.35M tokens ≈ **$4.9**.
- **Equivalence gate:** run greedy dev evals on v4r. Every area must be within 1 point of v4, and
  per-item agreement must be at least 90%. If v4r misses, stop and investigate; do not start RL from an
  unknown model.

`train_sft.py` gains two changes:
- Always save a final `weights/` state.
- New flags `--resume_state` and `--start_step`.

## 4. Objective and estimator (the math)

**Objective.** For prompt mixture D over the three tasks:

  J(θ) = Σ_task w_task · E_{x∼D_task} E_{y∼π_θ(·|x)} [R_task(x, y)]

There is no KL term; the reason is given under "KL penalty" below. Here `π_θ` is sampled at
temperature 1 (the cookbook warns against other temperatures, and the importance ratio assumes T=1).

**Estimator.**
- For each prompt, draw G answers and set `A_i = r_i − r̄`.
- Since `r̄ = (1/G) r_i + ((G−1)/G) r̄_{−i}` and `r̄_{−i}` is independent of `y_i`:

  E[A_i ∇log π(y_i)] = ((G−1)/G) · ∇E[R]

  This is unbiased up to a constant factor of 7/8 for G = 8, which Adam's scale invariance absorbs.
- `∇ log π(y) = Σ_t ∇ log π(y_t | y_<t)`, so the loss sums over tokens with the sequence advantage on
  every token. That is exact REINFORCE.
- Two common variants are rejected:
  - Dividing by |y| makes the effective objective E[R/|y|]. It rewards short correct answers more and
    long wrong ones less, which is a length bias the metric does not have.
  - Dividing by the group std reweights each prompt by 1/σ_p. That upweights nearly solved prompts and
    no longer maximizes the metric.
- **Loss:** `importance_sampling`, run synchronously with one optimizer step per batch. The run is fully
  on-policy, so the ratio is about 1 and only corrects sampler/trainer numeric mismatch. Watch
  `kl_sample_train_v1`; a healthy dense model shows about 2e-4.

**Which prompts carry signal.** With binary reward and pass rate p:
- A group is informative (not all-equal) with probability `1 − p^G − (1−p)^G`.
- The expected squared group advantage is proportional to `p(1−p)·(G−1)/G`.
- For G = 8, a group is informative with probability 0.57 at p = 0.1, 0.99 at p = 0.5 and 0.57 at
  p = 0.9.
- So prompts with p in [0.1, 0.9] at T=1 are the useful ones. They are selected by measurement
  (Phase 2), not guessed. Constant groups are dropped before training
  (`remove_constant_reward_groups=True`); they cost only their sampling, about 25% of a step.

**Why this matches a greedy-decoded eval.**
- RL with these rewards raises the probability of the answer modes that pass.
- Where T=1 already passes sometimes (0 < p < 1) but greedy fails, the main effect is pass@k → pass@1
  sharpening, which is exactly what flips greedy outcomes.
- Prompt selection therefore oversamples items that are greedy-wrong but sometimes right at T=1
  (Section 6).

**KL penalty: dropped, with the arithmetic.**
- The penalty adds `β(mean Δ − Δ_t)` per token.
- After about 100 low-learning-rate LoRA steps, per-token |Δ_t| is about 1e-2, so at β = 0.02 the term
  is about 2e-4 per token.
- The task advantage on every token is |A| ≈ 0.3–0.5, about 2,000 times larger. At that size the
  penalty changes nothing and costs about 15% of each step (scoring under the reference).
- A β strong enough to matter (≥ 1) would freeze learning in a 100-step run.
- Drift is controlled instead by:
  - a low constant lr (2e-5);
  - a short horizon (≤ 120 steps);
  - all three graded tasks being rewarded;
  - checkpoint selection on held-out dev data every 20 steps;
  - a cheap direct KL monitor: every 20 steps, score 64 fresh rollouts under v4 and log mean Δ, with a
    stop rule in Section 8.

## 5. Rewards (one function per task, unit-tested)

All rewards score exactly the text the graded eval would see, decoded with the eval caps.

**Math**
- **Reward:** R = 1 if `equivalent(answer_of(y), target)` (the same code as `verify/math.py` and the
  public scorer), and the answer stopped on its own within 4,096 tokens. Otherwise R = 0.
- **Guards** (R = 0):
  - more than one `ANSWER:` line;
  - an `ANSWER:` line that is not the last line;
  - an answer containing " or " when the target does not, which blocks hedging between candidates.
    A length cap was rejected, because real MATH answers such as matrices run past 100 characters.
- **Targets:** MATH train targets come from the dataset's boxed answer. Teacher-generated problems are
  used only when at least two independent teacher solutions agree on the target; others are dropped.

**IF (metric-exact).** IFEval final_acc = ¼(PS + PL + IS + IL), with PS, PL over N prompts and IS, IL
over K = N·k̄ instructions. Prompt i with k_i instructions, s_i strict passes and l_i loose passes
contributes

  (1/4N) · [ps_i + pl_i + (s_i + l_i)/k̄]

So the reward is `R = ¼(ps + pl) + (s + l)/(4k̄)` with k̄ = 1.54 (834 instructions / 541 prompts in
IFEval).
- It equals 1 for a fully passed prompt with k̄ instructions. It weights prompts with more instructions
  exactly as the metric does.
- Strict and loose use `verify/ifeval.py`'s `score()`, which mirrors the official loose variants. The
  same checkers that verified the IF-RLVR SFT data handle the IF-RLVR constraint types.
- Truncation at 1,024 tokens: the truncated text is scored as-is, because that is what the eval does.
- **Quality gate** (R = 0), to protect the held-out set from degenerate outputs RL would otherwise find.
  It is the v4 SFT filter (`if_quality_problem` in `select.py`): label-line shortcuts, under 4 words,
  top-word share above 0.25 at 30+ words. The gate is logged per step. If it fires on more than 5% of rollouts, that is a hacking signal
  (Section 8).

**Code**
- **Reward:** R = 1 if the extracted code (`extract_code`, the scorer's own extraction) passes all
  visible **and hidden** tests in a sandboxed run, within 10 s, and stdout contains a per-run random
  sentinel printed **after** the last assert. Otherwise R = 0.
- The sentinel closes the `os._exit(0)` / `sys.exit()` hole: exiting early returns code 0 without
  running the asserts. Hidden tests close the hole of hard-coding the visible asserts.
- **Static guards** (R = 0): `__eq__`/`__ne__` overrides (the always-equal object trick), and
  `sys.exit`, `os._exit`, `exit(`, `quit(`, `builtins`, `atexit`, `signal`.
- **Sandbox:** this is new for RL, which runs about 10k T=1 programs on this Mac.
  - `sandbox-exec` with a profile that denies network and file writes outside the temp dir;
  - `RLIMIT_AS` 1 GB, `RLIMIT_CPU` 10 s;
  - a fresh temp working directory, and `python -I`.

## 6. Prompt pools and selection

**Sources (train side only):**

| Task | Source | Exclusions |
|---|---|---|
| Math | MATH train (DigitalLearningGmbH/MATH-lighteval, train); teacher-generated problems with agreed targets | `math_dev` ids (`is_dev`), vault ids |
| IF | `if_rlvr_prompts` (allenai/IF_multi_constraints_upto5); our own constraint-sampled prompts (`constraints/sample.py`, train mode) | `HELD_OUT` types; `DEV_ONLY_IDS` (all dev unseen and new types); dev ids |
| Code | `code_tasks` (ours); `oci_tasks` | `is_code_dev` descriptions; harness-unsafe tasks |

- Every pool goes through `pipeline/leakage.py` against all eval and proxy sets before use. The report
  and counts go into `runs/rl1/manifest.json`, and preflight refuses to train without it.
- Math and code prompts use the **harness template only** (no paraphrases). RL should sharpen the exact
  format the graders send.

**Calibration (Phase 2), measured and not guessed:**
1. Draw a stratified sample of 300 prompts per task, by subject and level for math, constraint type for
   IF, and source for code.
2. Run G = 8 at T = 1 plus 1 greedy decode on v4r. Cost about $2.5.
3. Per stratum, estimate:
   - T=1 pass rate p;
   - the greedy pass rate;
   - the informative-group rate;
   - truncation rate, format-failure rate and mean length;
   - quality-gate rate (IF) and sandbox error rate (code).
4. **Sanity gate:** read 30 rollouts per task by hand, and check every reward branch fires at least once
   on real outputs (correct, wrong, truncated, guard). A reward that never fires, or fires on visibly
   good outputs, blocks Phase 4.

**Selection rule:**
- Within a task, sample strata in proportion to `n_s · E[p(1−p)]_s · (1 + g_s)`.
  - `p(1−p)` is the signal from Section 4.
  - `g_s` is the stratum's greedy-fail rate, which tilts toward items greedy gets wrong.
- Strata with an informative-group rate under 0.25 are dropped.
- The error analysis enters here: v4 dev math failures are 55 of 93 at level 5 and concentrated in
  Geometry and Intermediate Algebra; the IF counting types fail most often. Calibration confirms or
  corrects these patterns on train prompts, so we never tune on public test items.
- **Task weights** are proportional to `(informative rate) × (eval fail rate) / (cost per group)`,
  normalized, with each task at least 20%. Prior guess before calibration: math 40, IF 40, code 20.
- One pass, no prompt repeated. 120 steps × 64 groups uses about 7,700 prompts, far below pool sizes.

## 7. Training configuration

| Setting | Value | Why |
|---|---|---|
| Start | v4r `weights/` state, fresh Adam | Section 3 |
| LoRA rank | 32 (unchanged) | Continues the SFT adapter |
| Loss | `importance_sampling`, sync, `num_substeps=1` | On-policy, the cookbook's tested MATH setting |
| lr | 2e-5 constant | The cookbook's tested Qwen3.5-9B MATH value; about 1/24 of our SFT lr |
| Group size G | 8 | Section 4; prompts are prefiltered, and the cookbook ran G=8 too |
| Groups per batch | 64 (512 rollouts) | Tested batch shape |
| Steps | 120 maximum, plus a spend guard | Section 8 |
| Temperature | 1.0 | Required for a correct ratio |
| Token caps | math and code 4,096; IF 1,024 (`rollout_limits`) | Eval caps |
| Renderer | `role_colon`, prompts stripped | Identical to eval tokens |
| KL penalty | 0, with a monitor | Section 4 |
| Constant groups | removed | Section 4 |
| Save | sampler and state every 10 steps, TTL 14 days | Selection and resume |

## 8. Run phases, costs and stop rules

| Phase | What | Est. cost | Gate to continue |
|---|---|---|---|
| 0 | Code and unit tests: rewards, guards, sandbox, pools, leakage, env token caps, replay flags. No Tinker calls. | $0 | All tests pass, including adversarial hack tests (exit-early, always-equal, label-line, multi-answer) |
| 1 | Replay to v4r, then dev equivalence check | about $6 | Section 3 gate; **before 2026-11-22** |
| 2 | Calibration | about $2.5 | Sanity gate; pool weights written to the manifest |
| 3 | Smoke RL: 3 steps, 8 groups | about $1 | Rewards, caps, removal of constant groups and checkpoint saving all work end to end |
| 4 | Main RL: up to 120 steps; greedy dev eval at steps 20, 40, …, 120 | about $55 + $3 | Stop rules below |
| 5 | Full eval (public, dev, proxies) of the best 1–2 checkpoints | about $4–8 | Acceptance rule |
| | **Total** | **about $72–76** | Hard cap $80 |

Per-step cost estimate:
- About 300k training tokens at $1.46/M, minus about 30% for removed constant groups: about $0.31.
- About 170k sampled tokens at $0.81/M: about $0.14.
- Total about $0.45 per step. Calibration replaces these estimates with measurements before Phase 4.

**The spend guard is code, not a promise.** The trainer sums `rollout_usage` and training tokens every
step at list prices, and stops cleanly, saving a checkpoint, when Phase 4 reaches $55.

**Stop rules (automatic):**
- Mean response length of any task exceeds 2× its step-0 value, or math truncation exceeds 5%.
- `kl_sample_train_v1` exceeds 0.01, or the KL monitor shows mean Δ against v4 above 0.05 nats per
  token.
- The quality gate fires on more than 5% of IF rollouts, or a code guard fires on more than 2% of code
  rollouts.
- Any dev area at a checkpoint is more than 2 standard errors below v4. In that case, stop and select
  among earlier checkpoints.
- The training reward of any task falls for 30 consecutive steps (smoothed).

## 9. Evaluation and checkpoint selection

**Selection (Phase 4):** greedy dev eval at each 20-step checkpoint (math 479, code 500, IF 700).
Choose the checkpoint maximizing the dev sum, subject to every area being within 1 standard error of
v4.

**Statistics:**
- Paired dev tests have a 2σ minimum detectable effect of about 2.8 points per area (n ≈ 500, about 10%
  discordant pairs). Gains smaller than that cannot be confirmed in one set.
- Picking the best of 6 checkpoints inflates the winner by about +1.3σ of noise. The chosen checkpoint
  is therefore **confirmed on independent sets** in Phase 5: public scores, MATH test minus MATH-500,
  and HumanEval.

**Acceptance:** standing rule, judged per area on the public score, the dev score and the held-out
proxy together. The team decides and uploads.

## 10. Risks and how each is closed

| Risk | Closure |
|---|---|
| Reward hacking: IF label lines, code early exit or always-equal, math multi-answer | Guards in Section 5, adversarial unit tests in Phase 0, gate rates as stop rules |
| Reference answers wrong | Dataset targets for MATH train; two-teacher agreement for generated problems; calibration flags strata where greedy and T=1 both "fail" an easy problem |
| Overfitting public or dev | Dev-only types and dev ids excluded from prompts; selection on dev, confirmation on independent proxies |
| Drift on unrewarded behavior | All graded tasks rewarded; low lr; short run; KL monitor; checkpoint selection |
| Running untrusted code locally | `sandbox-exec` profile, rlimits, temp dir |
| v4 state expiring | Phase 1 before 2026-11-22; RL states saved with a 14-day TTL |
| Cost overrun | Spend guard in code; cost recalibrated after Phase 2 |
| Rule 2 violation | Leakage check on every pool; preflight refuses to start without a clean manifest |

## 11. Components (for the implementation plan)

**New `pipeline/rl/` modules:**
- `rewards.py`: pure reward functions and guards.
- `sandbox.py`: sandboxed code runner.
- `envs.py`: `MathEnv`, `IFEnv`, `CodeEnv` on the cookbook's single-turn `Env`, with per-env
  `rollout_limits`.
- `pools.py`: builds pools with exclusions, leakage check and manifest.
- `calibrate.py`: Phase 2 report and pool weights.
- `train_rl.py`: cookbook `rl.train.Config`, mixed dataset builder, spend guard, stop rules, KL
  monitor.

**Changes:**
- `pipeline/train_sft.py`: save the final state; replay flags.
- `pipeline/preflight.py`: RL manifest checks.

**Tests:** `tests/test_rl_rewards.py` (including the adversarial cases), `tests/test_rl_pools.py`,
`tests/test_sandbox.py`, and replay flag tests.

**Logging:** everything is logged in `EXPERIMENTS.md` under "rl1".
