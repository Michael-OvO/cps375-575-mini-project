# RL round (rl1) design, v2

Date: 2026-11-16.
- v1 was approved as the base (commit 2bcb85c).
- v2 adds the results of a literature review of 2025–2026 papers and lab reports. The review is in
  `reports/小模型 RLVR 方法调研.md`, with notes in `research_notes/小模型 RLVR 方法调研/`.

Nothing here has been run, except the infrastructure probes marked **measured**.

## 0. What changed from v1, and why

| Change | Evidence |
|---|---|
| **Per-domain batch-std scaling of advantages** | IF partial-credit rewards have a smaller within-group spread than 0/1 math and code rewards, so IF would get systematically less gradient. "Tricks or Traps" (2508.08221) found group-mean plus batch-std worked best. ScaleRL (2510.13786) found normalization choice mostly affects efficiency, not the end point. |
| **A 15-step random-reward control run** | On Qwen models, random rewards produced large fake MATH-500 gains ("Spurious Rewards", 2506.10947), and Qwen2.5-Math reconstructs MATH-500 at a 54.6% rate (2507.10532). |
| **IF prompts with 2–3 constraints mostly; a wider constraint-type spread; IF prompts filtered to pass rate (0, 0.6]** | IFBench (2507.02833): out-of-domain IF peaks at 3 constraints per prompt, more types beat more prompts per type, and more than about 50–100 prompts per type adds nothing. IFDecorator (2508.04632): filtering to hard prompts was worth +4.6 IFEval. |
| **Wider IF quality gate and a trap-prompt hack monitor** | IFDecorator and AdvancedIF (2511.10507) document placeholders, dummy bullets, repetition to hit counts, empty section markers and self-evaluation lines. |
| **Stricter code tasks:** ≥5 asserts with ≥2 hidden, a stub test, more static guards, a visible-pass/hidden-fail metric | DeepCoder, AceCoder (2502.01718) and Code-R1 on test quality; reward-hacking reports (2511.18397, ImpossibleBench). |
| **Mix changed to math 40 / IF 35 / code 25** | "To Mix or To Merge" (2602.12566, Qwen3-4B after SFT): one mixed batch matched separate per-domain runs at 33% of the compute, with little interference. Code gets a little more because of its 1-in-4 fail rate on MBPP. |
| **Optional teacher term: the 397B's per-token reverse KL, on IF groups only, behind a pre-flight check** | Thinking Machines' on-policy distillation (OPD) blog: 9–30× cheaper than RL for the same score, and it recovered IFEval 79 → 83. MiMo-V2-Flash: teacher log-ratio plus outcome advantage beat its RL'd teachers. 2605.12483: a teacher only helps if it was itself RL-trained, which the 397B is. |
| **Pass rates re-checked mid-run** | Polaris and ScaleRL: prompts get easier during training, so stale estimates waste groups. |
| **Our own training loop, built on the cookbook's 313-line `recipes/rl_loop.py`** | The changes above all touch the advantage step, which is simpler and more testable in a small loop than in the full trainer. |

**Kept, and confirmed by the review:**
- Group-mean advantages without per-group std, and a token-sum loss without length normalization (Dr. GRPO).
- Dropping constant groups (DAPO, ScaleRL).
- No KL penalty to v4 (IFDecorator: KL 0 beat 0.005).
- The `importance_sampling` loss with synchronous, one-step-per-batch updates. Thinking Machines' "LoRA Without Regret" ran this exact setup and found LoRA matches full fine-tuning in RL.
- lr 2e-5 at rank 32. Their best LoRA lr was about 10× the full fine-tuning lr; full fine-tuning RLVR papers use about 1e-6 to 2e-6.

**Considered and skipped:**
- **Clip-higher, GSPO, CISPO, GMPO, Clip-Cov/KL-Cov:** these fix ratio drift that appears only with off-policy, long or MoE runs. Our ratio stays about 1, and measured clip rates were about 0.3% ("Tricks or Traps").
- **Entropy bonus:** entropy collapse helps greedy pass@1.
- **80/20 forking-token training:** no gain at 8B.
- **pass@k objectives and negative-only reinforcement:** they protect pass@k, while we are graded greedy.
- **Long-horizon methods (ProRL, BroRL), critic-based methods (VAPO), and LLM-judge rewards:** low recall causes hacking ("Precision over Diversity").
- **OPD alone:** it loses the exact metric-aligned rewards. The teacher's per-token signal is also noisier at 397B scale (2608.31046).

## 1. Goal and success criteria

Start from v4 (IFEval 75.9, MATH-500 71.8, MBPP 73.2; dev math 71.4, dev code 70.3; HumanEval 75.6).

- **Accept rl1** under the standing rule: no area drops beyond about 2 standard errors against v4, and
  at least one area gains. An area is judged on its public score, dev score and held-out proxy
  together (Section 9). The team decides and uploads.
- **Budget:** $80 total, enforced in code.
- **Rule 2 (hard):** no IFEval, MATH-500, MATH test, MBPP or HumanEval item as a prompt in any form.
  - Also excluded: dev items, dev-only constraint types, `HELD_OUT` types, and IFBench test prompts
    (Section 6), in case the hidden IF set is IFBench-like.

**Honest expectation:**

| Area | v4 | Expected after rl1 | Evidence |
|---|---|---|---|
| IFEval | 75.9 | 78–82 | IFBench +11 and IFDecorator +11 over about 2k steps; Tulu 3 +1; we run about 100 steps |
| MATH-500 | 71.8 | 72–75 | Tulu 3 +1.7 MATH; short RLVR mostly sharpens an existing pass@8 |
| MBPP | 73.2 | 73–76 | Strong-coder RL gives MBPP +1–4 with HumanEval flat |

Reaching 80 is plausible only for IFEval.

## 2. Facts checked in code

1. **v4's final checkpoint can't be trained from. Measured:**
   - Tinker rejects `sampler_weights/v4` ("only weights/ checkpoints are supported").
   - The latest trainable state is `weights/v4-step1500`, which loads with its optimizer. Its TTL
     expires around **2026-11-22**.
2. **Centering:** cookbook advantages are `r − mean(group)`. The Tinker `importance_sampling` loss is
   `−ratio·A`, summed over tokens, with no clipping. GRPO's clipping bias, the mechanism behind the
   spurious-reward gains, is therefore absent. The control run (Section 8) checks the result anyway.
3. **Per-env token caps:** the rollout runner reads `env.rollout_limits`
   (`rl/rollout_runner.py`, line 329).
4. **Teacher scoring and the hybrid:**
   - On-policy distillation scores the student's exact token sequence. The code comment says to
     re-render when the teacher's renderer differs.
   - The cookbook's distillation trainer adds the teacher term to the env's own advantage, which is
     the hybrid we want.
   - Same tokenizer across Qwen3.5 sizes, so completion tokens carry over unchanged.
5. **Tested reference settings:** MATH RL on Qwen3.5-9B used `importance_sampling`, lr 2e-5, G=16,
   64 groups, 180 steps. GSM8K used G=8, 64 groups, lr 8e-5. OPD on the Qwen3.5-9B base used lr 1e-4
   at rank 128.
6. **Eval prompts:** inspect's math template, and the MBPP template with our own few-shot examples
   (`pipeline/formats.py`), stripped like the inspect adapter. Greedy decoding, capped at IFEval 1,024
   and MATH/MBPP 4,096 tokens.

## 3. Starting checkpoint: replay to v4r (Phase 1)

1. Resume `weights/v4-step1500` with its optimizer.
2. Replay steps 1501–1687 on the same deterministic batches with the same `lr_at` values.
3. Save a `weights/` state and sampler weights as **v4r**.

- **Cost:** about $4.9.
- **Gate:** greedy dev scores within 1 point of v4 in every area, and per-item agreement of at least
  90%.
- `train_sft.py` gains a final-state save and `--resume_state` / `--start_step` flags.

## 4. Objective and estimator

**Objective:** J(θ) = Σ_d w_d · E_{x∼D_d} E_{y∼π_θ}[R_d(x, y)], sampled at temperature 1.

**Per-group estimator (unchanged):**
- `A_i = r_i − r̄`. Because `r̄_{−i}` is independent of `y_i`, E[A_i ∇log π(y_i)] = ((G−1)/G)·∇E[R].
- RLOO is the same thing times G/(G−1), which the learning rate absorbs.
- Token-sum loss with the sequence advantage on every token is exact REINFORCE.
- Rejected:
  - per-answer 1/|y| normalization, which biases toward length;
  - per-group 1/σ normalization, which upweights nearly saturated prompts.

**Per-domain scaling (new).**
- After centering, divide every advantage of domain d in the batch by `s_d`, the standard deviation of
  that domain's non-constant-group advantages in this batch (floor 0.05).
- Within a domain this is one constant, so the direction of ∇J_d is unchanged and the exact metric
  alignment holds.
- Across domains it equalizes gradient scale. The mixture weights w_d then set each domain's share,
  as intended, instead of the accident of reward variance.
- The stepwise objective becomes Σ_d (w_d/s_d)∇J_d. Since s_d changes slowly, this is a
  per-domain learning rate set to equalize step size.

**Signal per prompt.**
- With binary rewards at pass rate p, a group is informative with probability `1 − p^G − (1−p)^G`.
  For G = 8 that is 0.57 at p = 0.1, 0.99 at p = 0.5 and 0.57 at p = 0.9.
- Prompts are drawn in proportion to p(1−p): learnability (2502.12272), as in Polaris and ScaleRL.

**Why it helps greedy evaluation.**
- Short RLVR mostly sharpens toward modes that already pass, raising pass@1 and greedy accuracy
  (Yue et al. 2504.13837, NeurIPS 2025; "RL's Razor"; "RL Squeezes, SFT Expands").
- The realistic ceiling per prompt is v4's own pass@8. Selection therefore tilts toward prompts that
  greedy gets wrong but T=1 sometimes gets right, which are exactly the ones sharpening can flip.

**No KL penalty to v4.**
- At β = 0.02, the per-token penalty β·|Δ_t| ≈ 2e-4 is about 2,000 times smaller than |A| ≈ 0.4, so it
  does nothing.
- A useful β would stall a 100-step run.
- Drift control comes from: low lr, short horizon, all graded tasks rewarded, checkpoint selection, and
  a direct KL monitor.

**Optional teacher term (Section 7b).** For IF groups only, add `−λ·(log p_θ(y_t) − log q_397B(y_t))`
per token, with λ chosen so this term's spread is 0.3–1× the task advantage's (measured in the
pre-flight). Unlike KL to v4, this pulls toward a stronger model.

## 5. Rewards (pure functions, unit tested with adversarial cases)

Every reward scores what the graded eval would see, under the eval's token caps.

**Truncation (all tasks): R = 0 if the answer hits its cap without stopping.**
- For math and code this is exactly the eval outcome: no `ANSWER:` line or no closed code block means
  a fail.
- For IF the eval would score the truncated text. But truncations are rare (12 of 700 dev items),
  almost all degenerate, and zero-on-no-EOS is the Tulu 3 / AdvancedIF practice that prevents
  rambling.
- DAPO's argument for masking truncations instead applies to 8k+ reasoning where correct answers run
  long. Our median math output is 190 tokens and 4,096-token hits are loops.

**Math**
- R = 1 if `equivalent(answer_of(y), target)`, using the same code as the public scorer.
- Guards (R = 0):
  - more than one `ANSWER:` line, or the `ANSWER:` line not last;
  - " or " in the answer when the target has none.
- **Targets:** MATH train boxed answers. Teacher-generated problems only where at least two
  independent teacher solutions agree.

**IF (metric-exact)**
- R = ¼(ps + pl) + (s + l)/(4k̄), with k̄ = 1.54 (834 instructions / 541 prompts). This is the exact
  per-prompt share of final_acc.
- Partial credit is kept: IFBench's reward is a sum of per-constraint scores. The one study favoring
  all-or-nothing used a noisy LLM verifier.
- **Quality gate, R = 0.** The v4 SFT filter (label-line shortcuts, under 4 words, top-word share
  above 0.25), plus:
  - placeholder copies such as `[name]`, `{x}` or `<placeholder>`, unless the prompt asks for
    placeholders;
  - dummy list items: two or more list items under 3 words, or identical items;
  - repetition used to hit counts: any 3-gram repeated 4 or more times, or one sentence repeated;
  - empty section markers: a section header with no content under it;
  - self-evaluation lines such as "I have followed all the constraints" or "(Word count: …)";
  - keyword stuffing: a required keyword appearing more than 3× its required count in a single line
    or as a bare list.

**Code**
- R = 1 only if all of these hold:
  - the extracted code passes all visible and hidden asserts in the sandbox, within 10 s;
  - stdout shows a per-run random sentinel printed after the last assert, which defeats
    `sys.exit`/`os._exit` before the asserts;
  - no static guard fires.
- Static guards: `__eq__`/`__ne__`/`__hash__` overrides; `sys.exit`, `os._exit`, `exit(`, `quit(`,
  `atexit`, `signal`; rebinding `print`, `AssertionError` or `builtins`; `import sys`/`os` unless the
  task text names them.
- **Sandbox:** `sandbox-exec` (no network, writes only to the temp dir), `RLIMIT_AS` 1 GB,
  `RLIMIT_CPU` 10 s, a fresh temp dir, `python -I`.

## 6. Prompt pools and selection

**Sources (train only):**

| Task | Source | Exclusions |
|---|---|---|
| Math | MATH train; teacher-generated problems with agreed targets | `math_dev`, vault |
| IF | `if_rlvr_prompts` (IF_multi_constraints_upto5); our constraint sampler (train mode) | `HELD_OUT`, `DEV_ONLY_IDS`, dev ids, IFBench test prompts (n-gram check) |
| Code | `code_tasks`; `oci_tasks` | `is_code_dev`; harness-unsafe; < 5 asserts; stub-passable |

- **Code task requirements:**
  - at least 5 asserts in total, with the 3 visible ones shown in the prompt (harness format) and the
    rest hidden;
  - the stored reference solution passes all of them;
  - **stub test:** `return None`, `return 0`, `return ""`, `return []` and `return <first arg>` each
    fail every assert. Tasks failing this test are dropped.
- **IF constraints per prompt:** target 60% with 2–3 constraints, 25% with 1, 15% with 4–5.
- **IF diversity:**
  - at most 120 prompts per constraint type in the run;
  - spread across every train-allowed type, IFEval types plus IFEvalG and our own train types;
  - wide ranges for numeric constraint parameters.
- Every pool passes `pipeline/leakage.py` against all eval and proxy sets plus IFBench test. Counts
  and reports go in `runs/rl1/manifest.json`, and preflight refuses to run without it.
- Math and code use the harness template only.

**Calibration (Phase 2)**
1. Sample 300 prompts per task, stratified: subject × level for math, constraint type and count for
   IF, source for code.
2. Run G = 8 at T = 1 plus one greedy decode on v4r (about $2.5).
3. Per stratum, record:
   - p, the greedy pass rate and the informative-group rate;
   - truncation, format failure and length;
   - gate and guard rates;
   - the visible-pass/hidden-fail rate (code).
4. **Sanity gate:** read 30 rollouts per task by hand, and check every reward branch fires on real
   outputs at least once. A reward that never fires, or fires on visibly good output, blocks Phase 4.

**Selection**
- **Within a task:** draw strata in proportion to `n_s · E[p(1−p)]_s · (1 + g_s)`, where g_s is the
  greedy-fail rate. Drop strata whose informative rate is under 0.25.
- **IF band:** prompts with p in (0, 0.6], following IFDecorator's (0, 0.5] result while keeping
  partial-credit variance.
- **Math and code band:** p in [0.125, 0.875].
- **Task weights:** prior 40 / 35 / 25. Each task's share is adjusted by at most ±10 points toward
  `(informative rate) × (eval fail rate) / (cost per group)`, normalized.
- **Mid-run re-check at step 60:** strata whose running informative rate fell below 0.3 are
  down-weighted to zero. The information comes free from the training logs.
- One pass, no repeated prompts. About 6,000–7,700 prompts are used.

### 7b. Optional teacher term (397B, IF only): pre-flight decides

It is turned on only if all of these pass on about 200 calibration rollouts already paid for. The
extra scoring costs about $1–3.

1. **Re-rendering is correct:** the prompt is rebuilt in the Qwen3.5 chat template (non-thinking,
   empty think block), the student's completion tokens are unchanged, and the stop token is masked.
   The token-alignment unit test passes.
2. **No thinking pull:** mean teacher log-ratio over the first 5 completion tokens is not more than
   2× the per-token mean elsewhere.
3. **Signal:** the teacher's sequence log-ratio separates reward-1 from reward-0 IF samples, with
   AUC ≥ 0.65.
4. **Cost:** one test call's logged usage matches the prefill price ($1.65/M, $0.33/M cached).
   Per-step cost with the term must stay ≤ $0.65.
5. **Rules:** confirm with staff that logprob supervision from the 397B counts as an allowed teacher.
   We assume yes, because PROJECT.md allows a larger model as teacher. Ask anyway.

If any check fails, run RLVR-only. Expected effect of the term: −1 to +2 points on average, with its
main value in protecting IF quality and resisting checker hacks. It is a hedge, not the main bet.

## 8. Phases, costs and stop rules

| Phase | What | Cost | Gate |
|---|---|---|---|
| 0 | Code and tests: rewards, guards, sandbox, pools, leakage, token caps, replay flags, advantage scaling, re-render alignment. No Tinker calls. | $0 | All tests pass, including the hack tests |
| 1 | Replay to v4r, then the dev equivalence check, **before 2026-11-22** | about $6 | Section 3 gate |
| 2 | Calibration, plus the teacher pre-flight | about $2.5 + $2 | Sanity gate; weights and teacher decision written to the manifest |
| 3 | Smoke run: 3 steps × 8 groups | about $1 | Every component works end to end |
| 4a | **Control:** 15 steps with Bernoulli(0.5) rewards, otherwise the real config; greedy dev eval at step 15 | about $7 | Recorded as the noise baseline |
| 4b | **Main run:** dev eval at steps 20, 40, …; spend guard $50 | about $50 + $3 | Stop rules below |
| 5 | Full eval of the best 1–2 checkpoints | about $5 | Acceptance rule |
| | **Total** | **about $76** | Hard cap $80 |

**Spend guard:** the loop prices every step from logged tokens at list prices, and stops with a saved
checkpoint when Phase 4b reaches $50.

**Stop rules (automatic):**
- Any task's mean length exceeds 2× its step-0 value, or math truncation exceeds 5%.
- `kl_sample_train_v1` exceeds 0.01, or KL to v4 exceeds 0.05 nats per token. The KL monitor scores 64
  rollouts under v4 every 20 steps.
- IF gate rate exceeds 5%, any code guard exceeds 2%, or the code visible-pass/hidden-fail rate
  doubles from step 0.
- Trap-prompt hack rate exceeds 10%. Trap prompts are 50 fixed IF prompts where a hack is the easy
  path, checked at every dev eval.
- A dev area drops more than 2 standard errors below v4; then select among earlier checkpoints.
- Smoothed training reward falls for 30 steps.

**Logged every step, per domain:** reward, informative-group rate, effective batch size, length,
truncation, entropy, ratio statistics, gate and guard rates, spend.

## 9. Evaluation and selection

- **Dev eval** (greedy; math 479, code 500, IF 700) at each 20-step checkpoint. Also pass@1 at T=1
  and pass@8 on a 100-item subset per task, to tell sharpening from capability gain.
- **Selection:** maximize the dev sum, with every area within 1 standard error of v4 and the dev
  unseen-type IF score not below v4's. The unseen-type split is the best proxy for the hidden IF set.
- **Statistics:**
  - McNemar or paired bootstrap for every difference. The per-area minimum detectable effect is about
    2.8 points.
  - Picking the best of 6 checkpoints inflates the winner by about 1.3σ.
  - Only the part of the gain above the control run's step-15 change counts as real.
- **Confirmation** on independent sets: public scores, MATH test minus MATH-500, HumanEval.

## 10. Risks and closures

| Risk | Closure |
|---|---|
| Reward hacking | Gates and guards in Section 5, adversarial unit tests, gate rates as stop rules, trap prompts, visible/hidden code metric, optional teacher term |
| Spurious gains (Qwen) | IS loss has no clipping bias; random-reward control; independent proxies |
| Wrong references or weak tests | Dataset targets or two-teacher agreement; ≥5 asserts verified by a reference; stub test |
| Overfitting public or dev | Excluded types and ids; selection on dev; confirmation on proxies |
| IF generalization gap (dev unseen 51 vs seen 67) | Type diversity with a per-type cap, 2–3 constraints per prompt, wide parameter ranges, selection on unseen-type dev |
| Drift and terseness (IF-only RL lowers quality) | All graded tasks rewarded; low lr; short run; KL monitor; optional teacher term |
| Untrusted code on this Mac | `sandbox-exec`, rlimits, temp dir |
| v4 state expiring | Phase 1 before 2026-11-22 |
| Cost overrun | Spend guard in code; costs recalibrated after Phase 2 |
| Rule 2 | Leakage checks; preflight refuses to start without a clean manifest |
