# rl1: RL with verifiable rewards on v4 — design (v4)

This file is the single source of truth for rl1: every number, rule and threshold is stated here once.
The implementation plan (`docs/superpowers/plans/2026-11-16-rl1-rlvr.md`) says how to build it and points
back here instead of repeating values. Nothing here has run yet except the probes marked **measured**.

## 1. Goal, acceptance, rules

- **Goal:** one RL round on v4 that gains on IF without losing math or code.
- **Accept** an rl1 checkpoint as the submission only if no area (IFEval, MATH-500, MBPP) drops more than
  2 standard errors below v4 and at least one area is above v4 on both the vault and public.
  The team decides and uploads; agents never submit or overwrite `evaluation/submission.json`.
- **Rule 2 (hard; a violation zeroes the project):** no IFEval, MATH-500, MATH test, MBPP or HumanEval item
  is ever a prompt or a target. Also excluded from training: dev and vault items, `HELD_OUT` and
  `DEV_ONLY_IDS` constraint types, IFBench test prompts and trap prompts. Public results never choose
  prompts, weights or checkpoints.
- **Budget:** rl1 has a hard cap of **$135** (Tier L, approved 2026-11-16), enforced by the ledger (§8).
  The user added $250 on 2026-11-17 and chose RL-first over another SFT round; that money is outside the
  rl1 cap, earmarked for rl2, the teacher term if approved, and a reserve, each use confirmed separately.
- **Expected outcome (planning estimate, not a promise):** IFEval 78–80 (v4 75.9), MATH-500 72–74 (71.8),
  MBPP 73–76 (73.2). Literature gains come from weaker starting models, so the low end is as likely.

## 2. Evidence: where the points are

Diagnosis only, from per-item public logs of v1–v4; no public item chooses training data.

| | v4 | Wrong in v4, right in an earlier version | Never right | Flipping across versions |
|---|---|---|---|---|
| MATH-500 | 71.8 | 61 (12.2 pts), mostly levels 3–4 | 80 (52 at level 5) | 133 |
| MBPP | 73.2 | 30 (11.7 pts) | 39 | 67 |
| IFEval prompt-strict | 70.1 | 73 (13.5 pts) | 89 | 194 |

- Flipping items (right only sometimes) are the 0 < p < 1 zone that RL sharpening fixes. The never-right
  core is out of reach for a short run. Dev shows the same: 22% (math), 27% (code), 33% (IF) of items flip.
- IFEval failures are mostly counting types: `keywords:frequency` 24/42, `number_words` 23/52,
  `forbidden_words` 17/49, `number_sentences` 17/52, `letter_frequency` 16/33, `capital_word_frequency` 12/25,
  `english_lowercase` 10/39. These seven are the "counting types" of §6.1.
- MBPP failures are all wrong code, none format. Math has 11 of 141 failures from loops or truncation.
- Our IF verifier agrees with the official prompt-strict on 541 of 541 v4 items (**measured**).

## 3. Starting point

- `sampler_weights/v4` cannot be trained from. `weights/v4-step1500` loads with its optimizer and its TTL is
  cleared (**measured**, `expires_at=None`).
- **Replay to v4r:** new run name `v4r` (running as `v4` would overwrite v4's logs), reading
  `runs/v4/train.jsonl`, resuming with optimizer, steps 1501–1687 at v4's schedule
  (`lr_at(step, 1688, 4.7297908091376354e-4)`, batch 32), `--no_publish`. Cost about $5.
- **Equivalence gate:** v4r vs v4's stored per-item dev results: McNemar p > 0.05 in every area and
  per-item agreement ≥ 85%. v4r's final `weights/` TTL is cleared.

## 4. Objective and advantages

- J = Σ_d w_d E_x E_{y∼π(T=1)} [R_d]. Loss: Tinker `importance_sampling` (−ratio·A summed over tokens, no
  clipping), pinned because `rl_loop` defaults to `stable_reinforce`.
- **Advantage:** A_i = r_i − r̄ per group of G. No std or length normalization. Constant groups have A = 0
  and are dropped, except as §6.3 and §6.4 allow.
- **Domain scaling:** coefficient c_d = mean_d'(S·L) / (S_d·L_d), with S_d the std of centered advantages in
  non-constant groups and L_d the mean response length, as an EMA (α 0.1) over previous steps only,
  initialized from calibration. Being fixed before the step's samples, it keeps each domain's estimate
  unbiased; it equalizes Σ|A|·tokens across domains so the group counts set the gradient shares.
- **No KL penalty** (too small to matter at useful β); a KL monitor replaces it (§8).

## 5. Rewards

All rewards are pure functions with tests on real data. **Truncation** (`stop_reason == "length"`) gives
R = 0 in every task, stricter than the eval, to teach stopping.

**Math.** R = 1 if the graded scorer (`equivalent(answer_of(y), target)`) accepts; no other guards, because
a hack that fools the graded scorer fools MATH-500 too. Targets: MATH train answers, or teacher problems
where two independent solutions agree.

**IF.** Checkers are routed by constraint id inside the shared `pipeline/verify/ifeval.py` (dev eval uses
the same path): the 25 IFEval ids → official `instruction_following_eval`; IFEvalG and IFBench-train ids →
`pipeline/constraints/ifevalg`; project ids → `pipeline/constraints/extra`. Official kwargs drop `None`
values (else the checker randomizes them); langdetect is seeded 0.
- R = ¼(ps + pl) + (s + l)/(4·1.54), with ps/pl prompt-level strict/loose and s/l instruction-level counts.
  Maximum 0.82 at k = 1 and 2.12 at k = 5 (matches IFEval's instruction weighting). Normalized pass rate
  p̂ = mean R / max R.
- **Quality gate (R = 0)**, each rule with its exempt types:

| Rule | Exempt |
|---|---|
| v4 SFT label-line filter | none |
| Placeholder copies `[name]`, `{x}`, `<placeholder>` | square-bracket, bigram-wrapping, title, number-placeholder types, and any type whose kwargs ask for brackets |
| Same sentence 3+ times | any id containing `copy` or `repeat`, and `two_responses` |
| 2+ identical list items | none |
| Self-evaluation lines ("I have followed all…", "(Word count: N)") | none |
| Under 4 words | `letters:*`, length types with upper bounds, any id containing `short` |

**Code.** R = 1 only if all hold: code extracted with `extract_code`; harness-safe
(`preflight.top_level_unsafe` false); no AST guard fires (calls/imports of `sys.exit`, `os._exit`,
`os.kill`, `os.system`, `exit`, `quit`, `subprocess`, `unittest.mock`, `inspect`, `ctypes`, `importlib`,
`sys._getframe`, `gc`; assignment to `builtins`, `print`, `AssertionError`; any `__eq__`/`__ne__`
definition); every visible and hidden assert passes, **verified in the parent process**: the sandboxed child
only evaluates each assert's model-dependent side and prints its `repr`; the parent parses it as a literal and
compares it with the expected value, which never enters the child. A program can print anything or exit
early, but it cannot pass a hidden test without producing the right value. Supported assert forms:
`E == L`, `L == E`, `E`, `not E`, `E is True/False/None`, `math.isclose(E, L, ...)`, `abs(E - L) < c`
(`<=`), with `L` and `c` literals. Checks whose passing value is guessable (bare `E`, `not E`, `is`, or
`==` against True/False/None/0/1) also require `E` to be a direct call of the solution's function. A pool
item with any other assert form is dropped (measured: 1.7% of `code_tasks`, 4.8% of `oci_tasks`).
- **Sandbox:** `sandbox-exec` denying network, fork and writes outside a fresh temp dir; `RLIMIT_CPU` 10 s,
  wall 30 s; RSS watchdog 512 MB (`RLIMIT_AS` fails on macOS, **measured**); 12 workers; stdout cap 64 KB;
  `python -I -B -c`.

**Phase 0 data gates (must pass before any paid step):**
- IF gate: fires on < 1% of the quality-filtered verified answers of every type with n ≥ 50.
- Code: the guard fires on ≤ 0.2% of reference solutions, and ≤ 2% of references fail their own tests.
  Every reference scoring below 1 (failing, harness-unsafe, guarded) is dropped from the pools.
- IF router vs stored verification: a type with > 1% mismatch is dropped from the pools; the gate fails if
  dropped types cover ≥ 5% of IF prompts.
- Every pool kwargs dict builds and is deterministic over 5 seeds (non-deterministic types are dropped).

## 6. Data and the training loop

### 6.1 Pools

| Task | Source | Exclusions |
|---|---|---|
| Math | MATH train; teacher problems with agreed targets | dev, vault |
| IF | `if_rlvr_prompts`; our constraint sampler | `HELD_OUT`, `DEV_ONLY_IDS`, dev, vault, IFBench test, traps |
| Code | `code_tasks`; `oci_tasks` | code dev; < 5 asserts; a trivial stub passes all asserts; harness-unsafe reference |

- IF mix: 25% one constraint, 60% two–three, 15% four–five; ≤ 120 prompts per type; counting types (§2)
  weighted 1.5×; target 9,000 IF prompts.
- 50 trap prompts (written by us, where a hack is the easy path) are kept out of every pool and measured
  at each checkpoint eval.
- `HELD_OUT` and `DEV_ONLY_IDS` types are never trained, so unseen-type IF dev keeps measuring
  generalization.

### 6.2 Calibration and schedule

- **Calibration** on v4r: 300 prompts per task, G = 8 at T = 1 plus one greedy decode. Strata with
  Beta(1, 1) shrinkage: math subject × level band (1–3, 4, 5); IF family × count bin (1, 2–3, 4–5); code
  source × category. Read 30 rollouts per task by hand; every reward branch must fire on real outputs.
- **Stratum weight** ∝ n_s · E[p̂(1−p̂)]_s · (1 + greedy-fail rate), with n_s the stratum's pool size; IF
  strata with p̂ > 0.6 get half weight. Strata with informative rate < 0.25, or absent from calibration,
  are not scheduled.
- **Task weights:** prior IF 40 / math 35 / code 25, each moved at most ±10 points toward
  informative rate × dev fail rate / cost per group (dev only). Groups per step from these weights.
- **Schedule:** one pass, no repeats, drawn up front and saved. Steps = main-run budget (§7) / estimated
  cost per step, computed once by `schedule.py` from calibration lengths at ledger prices with a 25%
  margin plus 10% for gated SFT; the same estimate reserves each step. Three extra steps at the end are
  reserved for the smoke test and never trained by the main run.

### 6.3 Optional teacher term (397B, IF only)

Off unless staff confirm the teacher is allowed and a pre-flight on calibration rollouts passes: re-render
the prompt in the Qwen3.5 template with completion tokens unchanged (boundary tokens masked); the
log-ratio on the first five unmasked completion tokens (tokens 2–6) is at most 2× the mean elsewhere; the
per-token mean log-ratio separates samples at their group's top reward from the rest with AUC ≥ 0.65;
measured cost ≤ $0.65 per step. When on: per-token
advantage c_d·A − λ(log π − log q); IF constant groups are kept; S_d excludes the teacher term.

### 6.4 Gated SFT on all-fail groups (HPT-style)

- **Trigger:** a math or code group whose 8 rollouts all score 0. (IF prompts are newly composed, so no
  verified answer exists.)
- **Demonstration:** only examples already in `runs/v4/train.jsonl`. A v4 row matches when the pool id is a
  dash-boundary prefix of its id (`mn-642-3` for `mn-642-3-long`) and the pool item's raw problem or task
  text appears in its user message, so two problems sharing a prefix never match. These rows passed every
  v4 filter, so there is no new leakage surface. Several matches: the shortest answer. No match: the group
  stays dropped and uses no demo slot.
- **Loss:** weighted NLL on the demo's answer tokens, per-token weight μ·c_d, μ = 0.5 (one demo weighs about like one
  informative rollout). At most 8 demos per step, the first 8 all-fail groups in schedule order (the
  schedule is already random). The demo enters the same `importance_sampling` call as a ratio-1 datum
  (sampler logprobs = the current policy's, one prefill), which gives exactly the weighted NLL gradient
  without relying on gradient accumulation across calls.
- **Cost** about 3–10% of a step. Logged per domain: `sft_groups`, `sft_tokens`. Switch:
  `config["gated_sft"]["on"]`, revisited at the pilot review if length or dev drops.

### 6.5 Configuration (the values the code reads from `runs/rl1/config.json`)

| Setting | Value |
|---|---|
| Base / LoRA | Qwen/Qwen3.5-9B-Base, rank 32, starting from v4r `weights/` with fresh Adam |
| Optimizer | Adam (0.9, 0.95, 1e-8), lr 2e-5 constant |
| Batch | G = 8, 64 groups per step |
| Loss | `importance_sampling`, one call per step (RL datums plus ratio-1 gated-SFT datums) |
| Sampling | renderer `role_colon`, prompts stripped, T = 1, top_p 1.0 |
| Token caps | math 4,096, code 4,096, IF 1,024 (`SamplingParams.max_tokens`) |
| Gated SFT | on, μ = 0.5, ≤ 8 demos per step |
| Teacher | off; λ = 0.5 if the §6.3 pre-flight passes |
| Checkpoints | `weights/` and sampler every 10 steps, TTL 1,814,400 s (21 days); TTL cleared on the selected one |
| Resume | one JSON per checkpoint: step, state and sampler paths, EMA state, RNG state, ledger total |
| Checkpoint eval | every 20 steps (§9) |
| KL monitor | every 20 steps, 64 rollouts scored under v4 |

## 7. Phases

Main-run budget = cap − spent − smoke ($1) − checkpoint evals ($14) − Phase 5 ($12). Paid commands that are
not part of `pipeline/rl` (dev, vault, public and proxy evals, the teacher pre-flight) reserve through the
ledger first and sync billing after.

| Phase | What | Cost |
|---|---|---|
| 0 | Code, tests, data gates (§5) | $0 |
| 1 | Replay to v4r, equivalence gate (§3) | ~$6 |
| 2 | Calibration, hand review, teacher pre-flight if approved, schedule | ~$4.5 |
| 3 | Smoke: 3 steps × 8 groups | ~$1 |
| 4a | **Pilot: 40 steps, then stop for the user's review** | 40 × the per-step estimate (~$25–40) |
| 4b | Continue from saved state, only after the user approves the pilot | the rest of the main-run budget |
| — | Checkpoint evals, about $1.2 each | ~$14 |
| 5 | Merge candidates, selection, vault and confirmation (§9) | ~$12 |

## 8. Ledger and pause rules

- **Ledger** `runs/rl1/ledger.jsonl`: every Tinker call logs tokens and list-price cost, survives
  restarts, and refuses work that would pass the cap. Total = max(local sum, Tinker billing since the
  rl1 start).
- **Hard pauses** (bug or real harm; save state and wait for review): sample–train KL > 0.01 at any step;
  trap hack rate > step-0 baseline + 10 points; from step 20, a domain's mean length > 2× its calibration
  baseline and more than 50 tokens above it, or truncation > 2× baseline + 2 points; from step 40, any dev
  area more than 2 SE below v4. Eval rules fire inside `ckpt_eval` and stop training before its next step.
- **Warnings** (logged to `runs/rl1/warnings.jsonl`, read at each review, training continues): the length,
  truncation and dev rules above before their start step; IF gate or code guard rate > baseline + 3
  points; code visible-pass/hidden-fail > baseline + 3 points; KL to v4 > 0.05 nats/token; reward falling
  across three consecutive 10-step windows by more than 0.02. Early RL is noisy; a warning alone never
  stops the run.
- **Hard stops:** the cap (exit 4), or 3 consecutive crashed steps.
- **Logged every step, per domain:** reward, informative rate, length, truncation, gate and guard rates,
  Σ|A|·tokens share, sample–train KL, gated-SFT counts, ledger total.

## 9. Evaluation and selection

- **Checkpoint eval** (dev split only, greedy): math 325, code 337, IF 461 items; plus pass@1 at T = 1 and
  pass@8 on 100 items per task, and the 50 traps. Dev sum = math + code + IF final_acc.
- **Resolution:** at about 10% discordance a paired 2-SE difference is about 3.5 points per area; picking
  the best of 10–20 checkpoints inflates the winner's dev score by about 2–4 points. Dev mainly catches
  regressions.
- **Native choice:** the best 3-checkpoint moving average of the dev sum, with every area within 1 SE of
  v4 and pooled unseen IF types not below v4 − 1 SE.
- **Merge candidates** (pre-registered in git before scoring; at most 3):
  1. **Tail average (default):** uniform average of the last 3–5 saved checkpoints in a window with no
     pause and no length drift, averaged in ΔW = (α/r)·B·A space (never A and B separately), cut to rank
     32 by exact truncated SVD; maximum and mean relative truncation error reported.
  2. **Interpolation toward v4,** λ = 0.6 from v4r (the equivalence-gated stand-in for v4) toward the
     native choice: only if a dev area regressed or truncation rose.
  3. **Extrapolation,** λ = 1.2: only if smoothed reward still rose over the last 30 steps.

  Merged weights reach Tinker through the experimental upload in tinker 0.39.0
  (`external_weights_upload_start/finish`, then `create_training_client_from_state` and
  `save_weights_for_sampler`). First, a round trip of the unmodified `weights/v4-step1500` export must pass
  the §3 equivalence gate against v4's stored dev items with ≥ 95% per-item agreement, or merging is
  dropped. Course permission is asked before a merged
  checkpoint can become the submission.
- **Decision:** the tail average replaces the native choice unless it loses on the dev sum. Candidates 2
  and 3 replace it only if their dev-sum margin exceeds 2 paired SE (SE of the sum = √Σ per-area paired
  SE², the areas being disjoint item sets) and no area is more than 1 SE worse.
- **Freeze, then confirm:** the choice and one fallback are written to `runs/rl1/selection.json` and
  committed. Only then: the vault (once), public scores, MATH test minus MATH-500 and HumanEval, all paired
  against v4. Confirmation can reject the choice in favour of v4; it never picks among rl1 candidates.
