# v2: one improvement round driven by the v1 error analysis

Date: 2026-11-14 (revised). Inputs: `reports/error_analysis_v1.md`, `runs/README.md`.

## Decisions so far

- v2 data comes from Opus 5.5 (teacher spend is outside the Tinker budget), verified by the real
  scorers. Self-distillation from Tinker models is on hold until a controlled probe shows it beats
  teacher data (pilot data and code kept: `pipeline/self_distill.py`, `data/sd_*`).
- Every generator below exists because of a measured failure, targets the items where v1 fails, and
  has a guard that keeps the target learnable for a 9B model under the evaluation limits.

## Principles for learnable data

1. **Target the failure, not the topic.** Each prompt pool is ordered by whether v1 currently fails
   it (failure mining on training-side items; never on dev or test items).
2. **Within reach.** A target must be something the student could produce: explicit intermediate
   steps, no leaps, and lengths that fit well under the evaluation caps (math 4,096, code 4,096,
   IF 1,024 tokens). Lengths are measured with the student's tokenizer, not the teacher's.
3. **One behaviour per change.** Each generator teaches one visible behaviour (reason longer and check
   on hard math; check the code against the given asserts; count precisely). Formats are fixed so the
   behaviour is easy to pick up.
4. **Adaptive, not uniform.** Easy items keep the short style that already works, so the model learns
   when to spend tokens rather than always spending them.
5. **Measured on the same failure.** Each change has one dev metric that must move.

## Failure mining (Tinker, about $5)

v1 answers every hard training math problem (levels 4-5; all 3,726 MATH-train and 6,000 of the 10,354 verified new)
and every training-side code task once, greedy, with the evaluation prompts. The pass/fail result
orders the `math-long` and `code-plan` pools. Dev and test items are never used.

## Run

1. Failure mining.
2. Pilot each Opus generator on 100 items; read samples for learnability (length, step granularity,
   format) and measure keep rate and student-token length.
3. Full generation: `math-long` on all v1-failed hard problems plus about 1,000 v1-correct level-5
   problems (so long reasoning is tied to difficulty, not only to failure); `code-plan` on about 3,000
   tasks (v1 failures first, then weak topics); `if-count` about 2,000 prompts; new constraint types
   about 2,000 prompts.
4. v2 mix: the v1 mix, with long solutions replacing short ones for the same hard problems, code plans
   replacing direct answers for the same tasks, and the new IF data added. Retrain from the base model
   (rank 32, recommended LR, one epoch); same overlap filter. About $35.
5. Evaluate: public, dev with per-item error tables, proxies, and IFBench once added. v2 replaces v1
   only if the metrics in the table move the right way and no public score drops by more than 1 point.
