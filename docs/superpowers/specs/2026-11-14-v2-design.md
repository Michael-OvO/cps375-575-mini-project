# v2: one improvement round driven by the v1 error analysis

Date: 2026-11-14. Inputs: `reports/error_analysis_v1.md`, `runs/README.md`. Status: draft for the team.

## What v1 tells us

v1 clears every threshold (IFEval 72.0, MATH-500 70.0, MBPP 75.1). The error analysis finds three
limits that more of the same data will not fix:

1. Math stalls on hard problems because SFT taught a ~200-token solution style. 40x more math data
   added 2 dev points. The base model, when it finishes its long reasoning, solves 18 of 24 level-5 dev
   problems; v1 solves 39% of level 5.
2. Code is written without checking it against the asserts shown in the prompt. Most failures are
   logic errors one pass over those asserts would catch.
3. Instruction following improved only on constraint types we trained on (held-out types 50% before and
   after 6,000 more examples). Counting constraints and 11% repetition loops on public IFEval are the
   other large losses.

## Approach: verified self-distillation on Tinker

All new data in v2 is sampled from models on Tinker and kept only if it passes the real verifier.
This needs no outside teacher (Claude's weekly limit resets 2026-11-20) and uses the existing
verifiers and runner. It is the "verified self-distillation" step the original spec planned for v2,
now aimed at the measured failures.

### Math: long reasoning for hard problems

- Problems: MATH train level 4 and 5 (3,726), plus verified teacher-new problems of level 4 and 5. All
  have trusted answers.
- Sample the **base model** (its natural long-reasoning mode) with the harness math prompt,
  temperature 0.8, 4 samples per problem, `max_tokens` 4,096.
- Keep a sample only if it finishes on its own, its `ANSWER:` line matches ground truth, it is at most
  3,000 tokens (headroom under the 4,096 eval cap), and it has no repetition loop. At most 2 kept
  traces per problem, shortest first.
- Training mix: these long traces replace the short solution for the problems they cover; levels 1 to 3
  keep the short style. The model should learn to think longer only when a problem is hard.
- Risk: longer outputs at eval mean more truncation. The 3,000-token cap on targets and the per-level
  mix limit this, and the dev run measures it directly (truncation count is in the error tables).

### Code: plan and check before the code block

- Problems: our verified code tasks (training side only).
- Sample the base model with the harness code prompt, 4 samples, temperature 0.8.
- Keep a sample only if it passes the given and hidden tests, has reasoning before exactly one
  ```` ```python ```` block (the MBPP scorer grades the first such block, so reasoning must not contain
  one), and is at most 1,500 tokens.
- Training mix: about half of code examples get the reason-then-code form, chosen from the tasks v1
  fails and the weakest topics (dates and times, custom sort keys, recursion, DP, rounding, gcd,
  two-pointer); the rest keep the direct form.

### Instruction following: breadth, counting, clean endings

- New constraint types: write 25 to 30 more verifiers (code only), with emphasis on structure and
  counting families we lack (per-line limits, punctuation counts, ordering, positional rules). Keep 6
  existing held-out types plus 6 of the new ones out of training to measure generalisation.
- Responses: rejection-sample **v1** at temperature 0.8, 8 samples per prompt, on fresh prompts with
  the new and the weak types (exact counts, letter frequency, 3 to 4 constraints). Keep strict passes
  under 600 words with no repetition loop. v1 already solves these sometimes; training on its verified
  successes raises how often it does so at temperature 0.
- Loops: every kept response ends cleanly by construction; add more long responses (400 to 600 words)
  that end properly, since loops start in long outputs.
- Claude responses for the new types are added after 2026-11-20 if time allows.

### Data fixes

- Remove the 6 ill-posed teacher math problems with "no such ... exists" answers.
- Dev set: drop instruction-following items no model or teacher can satisfy (checked by sampling), and
  report held-out performance per constraint type, not per prompt.

## Run

- Retrain from the base model on v1 data plus the new data (same settings: rank 32, recommended LR,
  one epoch). Same overlap filter. Estimated 40k to 45k examples, $30 to $40.
- Before full sampling, a 200-problem pilot per task measures keep rate, length and cost; full sampling
  only if the keep rate makes the volume worthwhile (math: at least 30% of hard problems get a trace).

## Gate and evaluation

- Same suite as v1: public (sanity), private dev with per-item error tables, proxies.
- v2 replaces v1 only if it wins on dev math level 4 and 5, dev code and held-out IF types, and no
  public score drops by more than 1 point. Truncation counts are reported per task.
- Add IFBench to `proxy_eval` as an independent unseen-constraint proxy.
